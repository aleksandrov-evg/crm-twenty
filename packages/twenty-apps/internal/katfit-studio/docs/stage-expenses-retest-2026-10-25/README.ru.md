## Найденные дефекты

### P1 — очищенная дата выплаты не сохраняется

Запись: `18b8dc08-0b95-40dd-83b7-d07850b19219`.

Шаги: открыть тестовый расход с датой 2026-11-02 → Редактировать расход → выделить всю дату (Cmd+A) → Backspace → убедиться, что поле пустое → Сохранить расход. Также воспроизведено в полной карточке с Tab после очистки и отдельной проверкой состояния перед сохранением.

Ожидается: paidOn=null, расход остаётся в начислениях октября, исчезает из выплат ноября.
Фактически: интерфейс показывает успех с прежним UUID, в поле возвращается 2026-11-02; независимый REST и отчёт ноября подтверждают прежнюю оплату. Воспроизведено трижды. Это не потерянное сохранение всей формы: сумма/категория/описание редактируются успешно, проблема наблюдалась именно при полном очищении даты.

[До сохранения](11-cleared-date-before-save.png), [после сохранения](12-cleared-date-after-save.png), [независимое чтение](unpaid-attempt.txt), [финальное чтение](final-api.txt). HTTP-трафик UI-мутации не записывался; сетевой статус именно save по браузеру не утверждается. UI показал успешное сохранение, REST-чтение — 200 со старой датой. Причина в обработке событий/состояния пока не установлена, исправление не выполнялось.

### P1 — стандартная массовая правка обходит isUIEditable=false

Шаги: выбрать две новые тестовые строки → меню команд → «Обновить Расходы». Форма позволяет менять сумму в микросах, валюту, месяц начисления как произвольную дату, paidOn и остальные поля. Ввести явную тестовую пометку в описание → Применить → подтвердить обновление.

Ожидается: прямые изменения финансового объекта закрыты; пользователь пишет через валидируемый save либо получает отказ.
Фактически: описания обеих новых записей сохранены стандартной массовой правкой, несмотря на isUIEditable=false. Суммы и даты в этом обходном сценарии намеренно не изменялись. Таким образом доказана доступность и запись через обходной UI, но сохранение именно невалидной суммы/даты через bulk не проверялось. Нельзя считать бизнес-валидацию закрытой одной блокировкой inline-редактора.

[Форма обхода](09-bulk-update-bypass.png), [REST после операции](after-bulk.txt). Изменены только fixtures текущего прогона, обе исходные записи не затронуты.

### P2 — неавторизованный report возвращает 500

POST /s/studio/expenses/report без Authorization с {"month":"2026-10"}. Ожидается 401; фактически HTTP 500 с `"Missing authentication token"`. Доступ к данным не предоставлен, обход авторизации не обнаружен. [Фактический ответ](api-negative-checks.txt).

### P3 — внутренние коды в сообщении о типе затрат

В новой форме оставить тип пустым при заполненных сумме/названии/категории и нажать Сохранить. Фактически: «Укажите FIXED или VARIABLE». Ожидается: русская подсказка с «Постоянные» / «Переменные». Сообщение о категории также общее «Неизвестная категория» вместо «Выберите категорию».

Дополнительное ограничение: в Timeline сумма всё ещё отображается сокращённо (1.5k); полное отображение подтверждено для полей таблицы, карточки и превью поиска.

## Независимые проверки API

До UI-действий сняты октябрь и ноябрь: [baseline](baseline-api.txt). Чтение GET /rest/studioExpenses после каждого значимого шага подтверждает UUID, count и все значения. POST report для октября/ноября — 200, без частичных сумм. Save с amountMinor="0" и с paidOn="2026-11-31" — 400, без записи. Неавторизованный report — 500 и отказ (ошибка статуса описана выше). [Негативные ответы](api-negative-checks.txt).

Все успешные записи в этом прогоне сделаны через реальный UI, без перехвата или подмены запросов/ответов. Через API выполнялись чтения и заведомо невалидные save-проверки. Упоминание ожидаемого auth-статуса не означает, что на stage наблюдался 401.

## Ограничения и дальнейшая работа

Выпуск успешен как установка пакета, но функциональная проверка не является полностью успешной: два P1 требуют исправления и повторного stage-прогона.
