# Расходы и данные для аналитики

Объект `studioExpense` — один расход в одной категории за один месяц начисления.
Доступен в меню CRM «Расходы» с таблицей всех полей. Ядро Twenty не меняется.

## Создание и редактирование в CRM

После установки обновления стандартное создание и прямая правка `studioExpense`
в UI отключены. Используйте закреплённую команду «Создать расход»; для изменения
выберите одну запись либо откройте её карточку и запустите «Редактировать расход».
Обе формы сохраняют через авторизованный маршрут `save`. UUID при редактировании
передаётся явно; редактирование не создаёт новую запись.

В форме сумма вводится в рублях, например `1 234,56` или `1234.56`; допускаются
только положительные суммы с точностью до копейки. Месяц выбирается без дня,
в CRM сохраняется первым числом. Дата выплаты принимает `ДД.ММ.ГГГГ` или
`ГГГГ-ММ-ДД`; пустое поле означает неоплаченный расход. Ошибка календарной даты
отображается в форме без потери введённого значения. В реестре и карточке сумма
отображается полностью с двумя знаками копеек.

Открытие формы и «Отмена» ничего не записывают. После успешного ответа показан
UUID; обновите реестр, чтобы увидеть новые значения. При неподтверждённом ответе
создания повторная отправка заблокирована: сначала найдите расход в реестре,
чтобы не создать дубль. Подтверждённый отказ проверки (400) позволяет исправить
поля и отправить форму снова. Прямой API CRUD остаётся вне бизнес-валидации.

Локальные проверки формы с моками (из корня монорепозитория):
`node_modules/.bin/vitest run --config packages/twenty-apps/internal/katfit-studio/vitest.expenses.config.mts`.
Они не заменяют повторный прогон на stage после установки обновления.

## Запись через API приложения

Авторизованный `POST /studio/expenses/save`:

```json
{
  "name": "Аренда за октябрь",
  "amountMinor": "6500000",
  "category": "RENT",
  "description": "Помещение студии",
  "costType": "FIXED",
  "accrualMonth": "2026-10",
  "paidOn": "2026-11-02"
}
```

Сумма — положительное целое число копеек **строкой**, до 12 цифр.
В CRM хранится CURRENCY RUB в микрорублях, расчёты идут через bigint без float.
`paidOn: null` означает, что расход начислен, но ещё не оплачен.
`accruedOn` в CRM — первое число месяца начисления. Даты календарные, без
смещения часового пояса. Для изменения передать `expenseId` и все поля расхода;
можно изменить дату оплаты или вернуть её в null.

Категории: RENT, TRAINERS, MARKETING, FEES, SUPPLIES, TAXES, OTHER.
Тип: FIXED или VARIABLE.
Ответ содержит `createStudioExpense.id` (201) либо `updateStudioExpense.id` (200).
Создание без expenseId не идемпотентно: после неопределённого сетевого ответа
сначала сверить реестр, не повторять создание автоматически.

Одна запись поддерживает одну полную выплату. Частичные выплаты и распределение
расхода между месяцами оформляются отдельными строками с соответствующими суммами.
Не создавать одновременно общий расход и его части: это удвоит итог.
Удаление ошибочной записи — стандартный soft delete CRM, с учётом прав оператора.

## Чтение для дашбордов

Авторизованный `POST /studio/expenses/report` с `{"month":"2026-10"}` возвращает:

- `accruedExpenseMinor`: все расходы, начисленные за месяц (для прибыли);
- `paidExpenseMinor`: все выплаты, совершённые в месяце (для денежного потока);
- `fixedExpenseMinor`, `variableExpenseMinor`: структура начислений;
- `byCategory`: обе суммы по каждой категории, включая нулевые;
- `expenses`: строки, начисленные **или** оплаченные в месяце;
- `currencyCode: RUB`, `unit: kopeck`: все агрегаты — строки целых копеек.

Например, аренда за октябрь, оплаченная в ноябре, уменьшает октябрьскую прибыль,
но денежный поток ноября. Пустой месяц возвращает нулевые строки и пустой реестр.
Пагинация читается полностью (до 10 000 строк); при превышении лимита, повреждённой
пагинации или некорректном ответе CRM частичные итоги не выдаются.
Некорректная прямая правка CRM (иная валюта, доли копейки, не первое число месяца,
неизвестная категория) даёт 409 с ID записи вместо молчаливого пропуска расхода.
Прямой CRUD CRM не выполняет бизнес-валидацию API: внешний UI должен писать через
`save`. Правила доступа к записям продолжают определяться ролями workspace.

## Финансовые границы

Этот контракт отдаёт расходную сторону и не подменяет доход поступлениями.
При подключении общего дашборда: прибыль = доход по оказанным занятиям минус
`accruedExpenseMinor`; денежный поток = поступления минус возвраты и
`paidExpenseMinor`. Возврат клиенту — не расход студии и не строка этого реестра.
Реестр оплат имеет накопленную сумму возврата без даты каждого возврата; для
корректного денежного потока возвратов по месяцам потребуется отдельный журнал.
Эта доработка не объявляет готовыми доход, возвраты и полную прибыль.

## Выпуск

Локальные проверки: `yarn typecheck`, `yarn test:unit`, `yarn twenty dev:build`.
После проверки плана установить обновление приложения штатными `plan/apply`
в stage, затем проверить создание, изменение, soft delete и отчёт на реальном
workspace. В рамках реализации stage и production не изменялись.
