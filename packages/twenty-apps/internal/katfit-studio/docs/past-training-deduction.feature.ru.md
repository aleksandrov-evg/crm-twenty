# Фича: внесение прошедшего занятия со списанием посещения

## Статус и назначение

**Статус:** proposed.  
**Владелец области:** KATFIT Studio.  
**MVP:** оператор одним подтверждённым действием вносит фактически состоявшееся занятие в прошлом и списывает одно посещение с выбранного пакета.

Документ заменяет сценарий «вручную изменить запись и остаток». Такая схема не подходит: остаток пакета должен объясняться неизменяемым журналом операций, а не редактируемыми счётчиками.

## Что есть сейчас

В приложении уже существуют необходимые сущности и связи:

| Область | Реализовано | Ограничение |
| --- | --- | --- |
| Занятие | `ClassSession`: начало, окончание, статус `COMPLETED` | Нет команды создания прошедшего занятия. |
| Запись клиента | `Booking`: клиент, занятие, пакет, продукт, статус `ATTENDED`, флаг `consumesVisit` | Нет серверной команды, которая безопасно создаёт или закрывает запись. |
| Пакет | `Membership`: статус, срок, кэш-счётчики `visitsGranted`, `visitsReserved`, `visitsConsumed`, `visitsAvailable` | Поля могут быть отредактированы напрямую; проверка исторического права не реализована. |
| Журнал | `MembershipTransaction`: `CONSUME`, `visitDelta`, `occurredAt`, `reason`, уникальный `idempotencyKey` | Нет связи операции с `Booking` и нет мутаций баланса. |
| Права | application function role может читать и обновлять все записи | Нет отдельной операторской команды/интерфейса и ограничений прямого редактирования. |

Это подтверждается также текущим README приложения: `membership balance mutations` прямо указаны как отсутствующие.

## Проблема с текущей инструкцией

Раздел [«Внесение прошедшей тренировки для списания»](../../../../../Docs/customer-journey-diagrams.md) описывает целевой, но пока нерабочий процесс. В KATFIT нет объекта «Тренировки», кнопки «Списать тренировку», поля комментария и автоматического пересчёта остатка. Фактические названия объектов — **Занятия**, **Записи**, **Пакеты клиентов**, **Операции пакетов**.

Инструкция также просит проверить исторический остаток. Это нельзя надёжно сделать только по текущим полям пакета: для этого нужен упорядоченный журнал операций и правила, как располагать задним числом внесённую операцию среди уже состоявшихся.

## Граница MVP

Входит:

- внесение одной прошедшей записи с результатом `ATTENDED`;
- создание отсутствующего прошедшего занятия или использование выбранного существующего;
- проверка клиента, пакета, времени занятия и отсутствия дубля;
- атомарное создание `Booking`, `MembershipTransaction(CONSUME)` и обновление кэш-счётчиков пакета;
- аудит: кто внёс, когда, фактическое время занятия, обязательная причина и источник;
- повторный вызов с тем же ключом не создаёт повторного списания.

Не входит в первую версию:

- массовая загрузка, резервирование будущих записей, отмены, no-show, отработки, возвраты и продления;
- автоматическое назначение подходящего пакета;
- исправление уже списанной записи обычным оператором;
- ретроактивная перестройка истории нескольких пакетов.

## Целевой сценарий

1. Оператор открывает клиента и выбирает команду **«Внести прошедшее занятие»**.
2. В форме указывает пакет, продукт/формат, фактическое начало и окончание, при необходимости существующее занятие, а также причину и источник сведений.
3. Система показывает результат проверки: пакет принадлежит клиенту, дата в прошлом, пакет был допустим на дату занятия, имеется доступное посещение, дубль отсутствует.
4. Оператор подтверждает операцию.
5. Система одним серверным вызовом создаёт или использует `ClassSession`, создаёт `Booking(ATTENDED, consumesVisit=true)`, добавляет `MembershipTransaction(CONSUME, visitDelta=-1)` и обновляет счётчики пакета.
6. Пользователь видит ссылку на созданную запись и новый остаток. В карточке пакета видна операция с причиной и фактическим временем занятия.

Если проверка не проходит, никаких записей и списаний не создаётся. Оператор получает понятную причину и создаёт задачу на разбор вне данной команды.

## Инварианты и бизнес-правила

- Операция доступна только для времени строго раньше текущего времени сервера; часовой пояс — часовой пояс workspace.
- Пакет должен принадлежать выбранному клиенту, иметь статус `ACTIVE` и покрывать фактическую дату: `activatedAt <= startsAt` и `startsAt::date <= expiresOn` (при заданных границах).
- Доступность проверяется по журналу, а не только по полю `visitsAvailable`. Счётчики обновляются как кэш из того же атомарного изменения.
- Один `Booking` может дать не более одного `CONSUME`; для этого потребуется связь `MembershipTransaction.booking` и уникальность операции списания на запись.
- Дубль — активная или посещённая запись того же клиента на то же занятие. Для создаваемого задним числом занятия минимальный ключ поиска: клиент + пакет + фактическое `startsAt`; продукт/формат используется как дополнительная проверка.
- При повторе одного `idempotencyKey` команда возвращает исходный результат. Конфликт ключа с другим payload — ошибка, а не новое списание.
- После создания запись, операция и источник не редактируются оператором. Исправление в следующей фиче делается компенсирующей операцией, никогда удалением `CONSUME`.

## Техническое решение

### Точка записи

Добавить Logic Function `studio-record-past-attendance`. Она будет единственной точкой записи для данного сценария и получит доступ через `CoreApiClient`. Для UI использовать command menu item на карточке Person и front component с формой/предпросмотром. HTTP-маршрут можно добавить только если потребуется внешняя интеграция; UI не должен напрямую выполнять CRUD над четырьмя сущностями.

Минимальный вход команды:

```ts
type RecordPastAttendanceInput = {
  personId: string;
  membershipId: string;
  productId: string;
  startsAt: string;
  endsAt: string;
  existingClassSessionId?: string;
  reason: string;
  source: string;
  idempotencyKey: string;
};
```

`actor` брать из execution context, а не из тела запроса. `source` и `reason` сохранить раздельно: первое — канал получения факта, второе — объяснение исключения.

### Изменения модели

1. В `MembershipTransaction` добавить nullable relation `booking` и обратную relation на `Booking`. Это обеспечивает трассировку списания до посещения.
2. Добавить в `Booking` обязательные для ручного заднего внесения поля `recordedAt`, `recordedBy` и nullable `recordingReason`/`recordingSource`, либо хранить их в связанной Note. Для аудита и отчётов предпочтительны поля объекта, а не свободный текст без структуры.
3. Запретить обычным операторам прямое создание и редактирование `MembershipTransaction`, `consumesVisit` и кэш-счётчиков `Membership`; писать их может только Logic Function.
4. Добавить уникальное ограничение (или проверку в единой команде, если metadata не поддерживает partial unique) для `CONSUME` на один `Booking`.

### Атомарность

Перед началом реализации нужно подтвердить, может ли установленная версия SDK выполнить все операции в одной транзакции базы. Если нет, MVP нельзя считать финансово корректным: нужны либо серверная транзакционная команда Twenty, либо compensating/reconciliation-механизм до включения в UI. Последовательность мутаций без транзакции недопустима.

Внутри атомарной операции:

1. Найти результат по `idempotencyKey`; вернуть его при точном повторе.
2. Заблокировать и перечитать пакет и его операции.
3. Проверить все инварианты, пакет и отсутствие дубля.
4. Создать недостающее `ClassSession` со статусом `COMPLETED` либо проверить существующее.
5. Создать `Booking` со статусом `ATTENDED` и `consumesVisit=true`.
6. Создать `CONSUME` с `visitDelta=-1`, `occurredAt=startsAt`, ссылкой на запись и заполненной причиной.
7. Пересчитать и сохранить счётчики пакета из журнала; вернуть идентификаторы и остаток.

## План реализации

### Этап 0 — зафиксировать решения

1. Утвердить, допустимо ли заднее списание, если сегодня остаток уже нулевой, но на дату занятия он был положительным.
2. Утвердить формулу исторической доступности: операции сортируются по `occurredAt`, затем по стабильному техническому tie-breaker; отрицательный промежуточный остаток запрещён.
3. Утвердить минимальную роль, лимит давности (рекомендуется 30 дней для MVP) и шаблоны причин/источников.
4. Проверить транзакционные гарантии Core API/SDK и выбрать поддерживаемую UI-поверхность command menu + front component.

### Этап 1 — данные и доступ

1. Добавить relation операции к записи, поля аудита записи и нужные индексы.
2. Подготовить миграцию/app plan и применить её сначала в staging workspace.
3. Обновить роли: оператор запускает команду, но не редактирует журнал и баланс напрямую.
4. Добавить представление «Требуют разбора» для отклонённых/неполных случаев только если решения этапа 0 этого требуют.

### Этап 2 — доменная команда

1. Реализовать независимые функции: загрузка контекста, проверка пакета на дату, поиск дублей, вычисление остатка из ledger, создание записей.
2. Реализовать `studio-record-past-attendance` с идемпотентностью и атомарной записью.
3. Возвращать структурированные ошибки: `MEMBERSHIP_NOT_OWNED`, `MEMBERSHIP_NOT_ACTIVE_AT_ATTENDANCE`, `INSUFFICIENT_HISTORICAL_BALANCE`, `DUPLICATE_ATTENDANCE`, `FUTURE_ATTENDANCE`, `IDEMPOTENCY_CONFLICT`.
4. Реализовать сверку: кэш-счётчики равны агрегации `MembershipTransaction`; расхождение видимо владельцу, но не исправляется молча.

### Этап 3 — операторский интерфейс и документация

1. Добавить command menu item **«Внести прошедшее занятие»** в Person.
2. Сделать форму с поиском пакета клиента, обязательными временем/причиной/источником и предпросмотром найденного дубля и остатка.
3. Перед финальным подтверждением показать пакет, дату, `-1 посещение` и остаток после списания.
4. По успеху показать ссылки на запись, занятие и операцию пакета; обновить данные карточки.
5. Заменить раздел в `Docs/customer-journey-diagrams.md` фактическими названиями и новым единым действием, убрав указание вручную менять статус/остаток.

### Этап 4 — тесты и выпуск

1. Unit-тесты для проверки даты, исторического остатка, поиска дубля и идемпотентности.
2. Интеграционные тесты: успешное списание; повторный запрос; нулевой/недостаточный исторический остаток; неактивный или чужой пакет; дубль; ошибка на одном из шагов без частичных данных; два параллельных запроса на последнее посещение.
3. E2E: оператор запускает команду из клиента, подтверждает предпросмотр и видит новую запись и операцию в пакете.
4. Выпустить в staging, сверить несколько тестовых пакетов с ledger, затем включить роль для ограниченной группы операторов.

## Критерии готовности

- Оператор не может случайно создать запись без списания или списание без записи.
- Повтор команды не уменьшает баланс второй раз.
- Любое списание можно связать с клиентом, занятием, записью, пакетом, оператором и источником.
- Нельзя списать пакет другого клиента, неактивный на дату пакет или пакет без исторически доступного посещения.
- Ошибка не оставляет частично созданных сущностей.
- Остаток в карточке пакета совпадает с журналом операций.

## Открытые вопросы владельцу

1. Какой максимальный срок заднего внесения допустим: 7, 30 или 90 дней?
2. Можно ли списывать, если сейчас остаток нулевой, но ledger показывает положительный остаток на дату занятия?
3. Должен ли оператор иметь право создавать отсутствующее занятие, или только выбирать существующее?
4. Нужны ли причины и источники как фиксированные списки для отчётности, и какие значения обязательны?
5. Кто вправе делать корректировку ошибочного списания: владелец, администратор или отдельная финансовая роль?
