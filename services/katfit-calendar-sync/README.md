# KATfit Calendar Sync

Отдельный сервис синхронизации расписания Яндекс / CalDAV и Twenty CRM.
Twenty server и worker остаются на официальном образе `twentycrm/twenty`.
Пакет не включён в Yarn / Nx workspace Twenty и устанавливается независимо.

## Текущее состояние

Перенесены условная запись CalDAV, three-way merge расписания, обновление генерируемого блока описания и PostgreSQL-хранилище операций с lease / fencing.
Есть независимая сборка, миграция собственной схемы и `/healthz`.
Ответ health содержит `synchronizationEnabled: false`: полный двусторонний обмен ещё не завершён. Создание новых одиночных занятий доступно отдельно под CALENDAR_CREATE_SEND_ENABLED, переносы и переименования связанных будущих одиночных занятий — под CALENDAR_SCHEDULE_SEND_ENABLED; оба требуют управляемой активации; по умолчанию все фоновые флаги выключены.

Добавлены независимый authenticated CalDAV transport и discovery Яндекс-календарей на настоящем tsdav. Пароль передаётся только на https://caldav.yandex.ru; DNS-адреса проверяются в lookup реального сокета, приватные/служебные диапазоны отвергаются. Redirect автоматически не следует; discovery принимает только разрешённые same-origin Location, условная запись запрещает redirects. Запросы и ответы ограничены 2 MiB, сетевое время — 15 секунд; XML DTD/entity declarations отвергаются. Проверки транспорта и discovery используют управляемые ответы без обращения к реальному аккаунту.

Добавлены хранение подключения и шифрование пароля приложения AES-256-GCM с привязкой к workspace, connection ID и логину. Подключение создаётся только в PREVIEW. Публичные результаты хранилища не содержат пароль или ciphertext; отключение удаляет сохранённый секрет. Изменение состояния и замена пароля защищены configurationVersion; новый пароль требует повторного preview. Это операции внутреннего хранилища, не публичный API.

Добавлены фоновое read-only чтение календарей, хранение ресурсов и транзакционный inbox. По умолчанию polling выключен. Добавлены разбор одиночных событий, подготовка кандидата и отдельный read-only CRM lookup; разбор подключён к отдельному фоновому preview worker, CRM lookup доступен в операторском CLI и отдельном фоновом worker. Обработка серий и интерфейс ещё не реализованы. По умолчанию входящие события не изменяют CRM; управляемое создание описано в разделе активации. Команды discovery и connect доступны отдельно: discovery читает список календарей, connect сохраняет выбранное подключение без изменения событий.

## Фоновое чтение календаря

После миграций и сохранения подключения в PREVIEW можно явно включить `CALENDAR_POLLING_ENABLED=true`. Нужен тот же `CALENDAR_ENCRYPTION_KEY` и key ID, которыми зашифрован пароль. Compose передаёт эти переменные сервису; при локальном запуске используйте окружение или `node --env-file=.env dist/main.js`.

Poller выбирает только PREVIEW / ACTIVE подключения, получает lease и читает полный VEVENT inventory с исходными master/exception ресурсами без разворачивания повторений. Следующий успешный опрос планируется через 60–70 секунд. PAUSED, DISCONNECTED, AUTH_REQUIRED и ERROR не опрашиваются. 401 переводит подключение в AUTH_REQUIRED, 403 — в ERROR; сетевые/неполные ответы повторяются с задержкой без продвижения readGeneration. Для восстановления нужен отдельный операторский flow; автоматического resume ещё нет.

В одной транзакции сохраняются:

- `calendarResource`: исходный VCALENDAR, ETag, SHA-256 содержимого, версия ресурса и поколение последнего наблюдения;
- `calendarInbox`: UPSERT для нового/изменённого ресурса, без дублей при повторном снимке;
- readGeneration и время успешного чтения подключения.

Отсутствие ранее известного ресурса создаёт только MISSING_CANDIDATE. Оно не отменяет занятие, не удаляет историю и требует дальнейшей проверки фактического удаления. Возвращение события создаёт новую UPSERT-версию. Ошибка одного члена multi-status, повреждённый XML, отсутствующий/слабый ETag или неверный href отклоняют весь снимок. Ошибка записи в середине пачки откатывает ресурсы, inbox и поколение вместе.

Результат чтения фиксируется только при действующем lease, неизменной configurationVersion и разрешённом состоянии подключения. Пауза/отключение не дают сохранить устаревший снимок. SIGTERM дожидается текущего цикла и завершает polling перед закрытием БД. Это защита входящего чтения; создание в CRM и обогащение календаря включаются отдельными флагами, описанными ниже.

Текущий транспорт — полный REPORT, не incremental sync-token. Максимум 2 MiB и 2000 ресурсов на снимок; при превышении полный импорт отклоняется. Поддержка больших календарей, delta cursor, подтверждение удалений, обработка уже связанных прошедших занятий и доменные мутации — следующие этапы. В `/healthz` поле calendarPollingEnabled отражает включение чтения, а synchronizationEnabled остаётся false, пока остаются нереализованные сценарии отмен, серий и операторского разрешения конфликтов.

## Фоновая подготовка событий из CalDAV

После применения четвёртой миграции включите `CALENDAR_PREVIEW_ENABLED=true` (по умолчанию false; переменная передаётся Compose). При совместном `CALENDAR_POLLING_ENABLED=true` события проходят путь CalDAV → calendarResource / calendarInbox → calendarImportPreview без локальных файлов. Preview можно включить отдельно для уже накопленного inbox; ему не нужен ключ расшифрования и доступ к сети.

Воркер раз в секунду подготавливает одну запись для PREVIEW/ACTIVE подключения. Он сохраняет READY с кандидатом, NEEDS_REVIEW с причиной или SUPERSEDED для устаревшей версии. Фоновая версия требует `format` и `capacity` в KATFIT-блоке описания: defaults из локального preview CLI к подключениям не применяются. Настройка defaults на уровне подключения ещё не добавлена. Исчезновение события требует проверки удаления и не отменяет тренировку.

Блокировка подключения сериализует подготовку со снимком календаря и pause/disconnect. Результат уникален по inboxId + configurationVersion; изменение конфигурации создаёт новый результат, сохраняя историю. Параллельные воркеры не создают дубли. На этапе preview inbox остаётся PENDING: APPLIED устанавливается только при подтверждённой финализации создания, описанной ниже. Ошибка транзакции повторяется с задержкой; остановка процесса ожидает завершения текущей операции.

`calendarImportPreview` — история. Для актуальных результатов используйте `calendarCurrentImportPreview`, ограничивая запрос workspaceId и connectionId. Представление исключает старую resourceVersion/configurationVersion, исчезнувшие UPSERT, вернувшиеся MISSING_CANDIDATE и отключённые/приостановленные подключения. READY означает только корректного кандидата на момент подготовки: перед будущей мутацией нужно повторно проверить актуальность, время начала, связь с CRM и полномочия. Результаты не исполняются автоматически.

Пример операторского запроса в собственной БД сервиса (параметры передаются драйвером):

```sql
SELECT "inboxId", "decision", "reason", "candidate"
FROM calendar_sync."calendarCurrentImportPreview"
WHERE "workspaceId" = $1 AND "connectionId" = $2
ORDER BY "createdAt";
```

`/healthz` сообщает calendarPreviewEnabled. synchronizationEnabled остаётся false: в этом worker нет HTTP-запросов к CRM, записей в календарь и операций с участниками/финансами. Таблицы preview содержат данные закрытого календаря и должны иметь тот же режим доступа и резервного копирования, что calendarResource.

## Фоновое сопоставление с CRM и сохранённые связи

Пятая миграция добавляет `calendarSessionLink` и `calendarCrmReconciliation` только в БД сервиса. Включение: `CALENDAR_CRM_LOOKUP_ENABLED=true`, вместе с `TWENTY_WORKSPACE_ID`, `CALENDAR_CONNECTION_ID`, `TWENTY_API_URL`, `TWENTY_API_TOKEN`. Один процесс выполняет CRM lookup строго для указанной пары workspace/connection; он не использует один токен для всех подключений в БД. Оператор должен подтвердить принадлежность токена workspace. Для нескольких workspace необходим отдельный механизм выбора credentials; он ещё не реализован.

При наличии актуального READY preview worker получает lease на 45 секунд и выполняет GET к публичному API вне SQL-транзакции. После ответа повторно проверяет состояние подключения, configurationVersion, resourceVersion и поколение lease. Запоздалые ответы после изменения/паузы/перехвата lease отбрасываются. Внешних изменений нет.

Результаты:

- LINKED: точное совпадение recordingKey, связь `(workspace, connection, UID, single) → classSessionId` сохранена;
- CREATE_CANDIDATE: успешный пустой ответ для ещё не связанного события, без создания тренировки;
- NEEDS_REVIEW: неоднозначный ответ, ошибка доступа/схемы, два актуальных READY ресурса с одним UID, смена связанной CRM identity или исчезновение ранее связанной тренировки;
- PENDING / CRM_UNAVAILABLE: сеть/временная ошибка, повтор не ранее чем через 60 секунд.

Уникальность связи дополнительно запрещает присвоение одной тренировки двум UID внутри подключения. Изменение времени и названия при прежнем UID сохраняет ключ. Другой resourceId для уже связанного UID требует проверки перемещения; автоматически переносить связь на другой href пока нельзя. Проверка дубликатов использует подготовленные READY-ресурсы, а не все сырые/неподдерживаемые VEVENT; перед будущими записями требуется полная проверка идентичности. Ссылки на CRM — внешние UUID без FK в базу Twenty.

`observedSession` хранит последний прочитанный снимок CRM, не общую подтверждённую базу three-way merge: календарь и CRM ещё могут различаться. LINKED не означает синхронизированное расписание. Сам lookup не меняет inbox на APPLIED. Результаты сопоставления надо читать через join с `calendarCurrentImportPreview` по inboxId/configurationVersion и с фильтром workspaceId/connectionId; таблица reconciliation содержит также исторические записи. Перед будущим созданием нужна свежая проверка отсутствия, перед обновлением — повторное чтение и доменный compare-and-set.

Worker обрабатывает каждую версию один раз после успешного lookup; изменения только на стороне CRM пока не отслеживаются. Review и CREATE_CANDIDATE не повторяются сами; операторский requeue/review flow ещё нужен (изменение конфигурации или события создаёт новую проверку). `/healthz` сообщает calendarCrmLookupEnabled, а synchronizationEnabled остаётся false. Тесты используют управляемый CRM lookup; настоящие аккаунты не затронуты.

## Подготовка создания новой тренировки

Шестая миграция добавляет `calendarSessionCreateIntent`. `CALENDAR_CREATE_PREPARATION_ENABLED=true` включает локальную подготовку для заданных TWENTY_WORKSPACE_ID / CALENDAR_CONNECTION_ID; по умолчанию false. Для полного входящего пути нужны polling, preview и CRM lookup. Подготовка может работать по ранее накопленным результатам без credentials и сетевого доступа.

Из актуального READY + CREATE_CANDIDATE формируется команда публичного приложения `/s/studio/sessions/create`: name, sessionFormat, startsAt, durationMinutes, capacity, status=PLANNED, прежний idempotencyKey и пустой participants. Не передаются завершение, посещения, списания или участники. Повторный запуск сохраняет исходную команду. Если новая версия с тем же UID снова становится CREATE_CANDIDATE, старый payload не перезаписывается: intent получает NEEDS_REVIEW / SOURCE_CHANGED_AFTER_PREPARATION. После неясного результата нельзя менять параметры повторного запроса.

Перед подготовкой проверяются UID во всех присутствующих сырых ресурсах, включая события, которые не стали READY (all-day, серии и прочие). Дубли UID, отсутствие доверенной идентичности любого ресурса, появившаяся связь с CRM и прошедшее начало требуют review. Это проверка локального последнего снимка; свежий CalDAV/CRM read перед реальной отправкой всё ещё обязателен.

Таблица intents — сохранённое намерение, не очередь разрешённых к исполнению команд. PREPARED само по себе не доказывает актуальность: событие могло исчезнуть, измениться или подключение могло остановиться. Будущий executor должен сверять inbox/configurationVersion, state подключения, текущую версию/ETag, UID и отсутствие CRM-связи непосредственно перед отправкой. Этот flag включает только локальную подготовку; executor создания включается отдельно после активации, как описано ниже. `/healthz` содержит calendarCreatePreparationEnabled, synchronizationEnabled остаётся false.

Sender команды создания подключается к worker только при явном CALENDAR_CREATE_SEND_ENABLED и подтверждённой активации. Он проверяет строгую схему, допускает только PLANNED без участников, отправляет ровно один POST, запрещает redirects, ограничивает ответ 2 MiB/15 секунд и проверяет success/classSessionId/duplicate. Ошибка сети, неверный ответ или HTTP 400/409/500 дают unconfirmed: ответ не доказывает отсутствие тренировки. 401/403 сообщаются отдельно. Секреты и серверные сообщения не возвращаются. Sender проверен управляемыми ответами, настоящие POST не выполнялись.

В исходниках приложения katfit-studio найден уникальный индекс recordingKey и повтор по idempotencyKey. Но создание тренировки и SESSION_CREATED выполняются отдельно. Поэтому REST lookup занятия после timeout недостаточен для доказательства завершённого журнала; восстановление должно сверить журнал/исходную команду и при необходимости повторить тот же POST с неизменным payload и ключом. Наличие индекса и маршрута на конкретном стенде ещё нужно проверить. Атомарные изменения существующего расписания и финансовых действий этим не решены.

Исправлена гонка в общей очереди операций: advisory lock теперь берётся отдельным запросом до чтения очереди в транзакции, чтобы snapshot следующего claimant включал commit предыдущего. Проверка выполняет 20 раундов одновременного захвата тремя вызовами на двух независимых DataSource.

## Сверка и восстановление создания

Добавлен inspector через публичные GET `/rest/classSessions` и `/rest/studioEvents`. Он ищет занятие по frozen recordingKey, проверяет creationRequest (PLANNED, пустые participants, пустое attendanceReason) и формат. Журнал выбирается по ID занятия: команда приложения использует этот UUID также как ID SESSION_CREATED. Проверяются id, classSessionId, eventType, outcome, idempotencyKey, детали имени/времени/вместимости и отсутствие участников. Ошибки схемы, неправильный фильтр, неполная пагинация и неверный журнал не считаются успехом.

Результат inspector:

- absent — занятие не найдено;
- incomplete — занятие совпадает с исходной командой, но SESSION_CREATED отсутствует;
- confirmed — создание подтверждено соответствующим журналом;
- needs-review — идентичность/параметры/журнал неоднозначны;
- unavailable/auth-required/forbidden — сверка не выполнена.

confirmed доказывает выполнение исходного создания, а не совпадение текущего расписания с календарём. Позднейший статус COMPLETED не мешает подтвердить существующий исходный журнал. Формат в журнале не хранится: если текущий формат отличается, inspector требует review. Если журнала нет, изменённое занятие автоматически повторять нельзя.

Операторская команда читает именно сохранённый payload из собственной БД, без ручного ввода параметров и без POST:

```bash
# Используются CALENDAR_DATABASE_URL, TWENTY_WORKSPACE_ID, CALENDAR_CONNECTION_ID,
# TWENTY_API_URL, TWENTY_API_TOKEN и при необходимости TWENTY_ALLOW_INSECURE_HTTP.
# Укажите исходный UID события:
CALENDAR_EVENT_UID='uid-from-calendar' node --env-file=.env dist/inspect-creation.js
```

Команда возвращает JSON статуса, завершает процесс с кодом 0 только для confirmed. БД не меняет, не сохраняет proof и не активирует подключение. Ошибки конфигурации/доступа к сохранённому заданию выводятся без SQL, payload и credentials. Проверена на временной БД и локальном HTTP mock: ровно два GET, неизменность intent, без реальной CRM.

Добавлен модуль `recoverCalendarSessionCreation`, используемый отправляющим worker после активации. Порядок: inspect → только для absent/incomplete внутренняя проверка authorizeSend → один POST неизменяемой копии команды → повторный inspect. authorizeSend — callback будущего executor для проверки lease/state/source, а не вопрос пользователю. Без подтверждения guard POST не выполняется. Новое absent-событие с прошедшим началом не создаётся. Если уже известен classSessionId, его отсутствие/подмена требуют review; ID перед POST, в ответе POST и подтверждённом журнале должны совпадать.

Потерянный ответ POST может завершиться confirmed после сверки журнала. Один успешный POST без подтверждённого журнала остаётся unconfirmed. Модуль не запускает скрытые повторы: следующая попытка снова начинается со сверки и использует прежний payload/key. Ошибка sender также остаётся unconfirmed. Параметры копируются и замораживаются до первого await.

Durable lease/attempt/proof, сохранение известных ID, live CalDAV guard и управляемая активация создания реализованы ниже. До включения на живом стенде нужно проверить установленное приложение и его поведение; UI/review/requeue flow ещё не завершён. Существующая проверка guard и POST в разных системах не образуют распределённую транзакцию; изменение источника после проверки нужно обнаруживать и выносить в отдельный конфликт. Отправка включается только отдельным CALENDAR_CREATE_SEND_ENABLED после активации.

## Сохранённые попытки и фоновая сверка создания

Седьмая миграция добавляет calendarCreationExecution и calendarCreationAttempt. Включение `CALENDAR_CREATION_RECOVERY_ENABLED=true` запускает фоновую **read-only** сверку сохранённых intents для указанной пары TWENTY_WORKSPACE_ID / CALENDAR_CONNECTION_ID с workspace-scoped API credentials. По умолчанию false. Сам по себе recovery flag не включает POST. Sender создаётся только при дополнительном CALENDAR_CREATE_SEND_ENABLED=true; в PREVIEW worker всегда выполняет только чтение. В health отражается calendarCreationRecoveryEnabled; synchronizationEnabled остаётся false.

Execution хранит состояние PENDING/RUNNING/RETRY/CONFIRMED/NEEDS_REVIEW, поколение и срок lease, известный classSessionId, последний результат и дату повтора. Attempt хранит отдельную строку на каждое поколение: первоначальную и последнюю сверку, sendStartedAt, sendResult и итог. Команда остаётся в исходном immutable intent; она не генерируется заново при восстановлении.

В одном подключении одновременно выполняется одна попытка. Lease — 120 секунд; истёкшая попытка забирается первой с новым поколением. Прежний worker не может подтверждать или записывать результат в текущее состояние. Все записи проверяют scope, configurationVersion, PREVIEW/ACTIVE и действующий lease. Пауза/смена конфигурации отклоняют результат; после возобновления и истечения lease повтор снова начинается со сверки, а не с POST. История старой попытки не удаляется.

Readonly worker записывает известный ID из incomplete/confirmed до возможного будущего повтора. Пропавший или изменившийся известный ID требует review. absent/incomplete/unavailable/unconfirmed откладываются минимум на 60 секунд; ошибки доступа и несоответствия завершаются NEEDS_REVIEW. CONFIRMED требует сохранённой сверки соответствующего SESSION_CREATED с тем же recordingKey и classSessionId, одного ответа POST недостаточно. CONFIRMED больше не выбирается после перезапуска.

Добавлены внутренние методы будущего executor и интеграционная проверка с injected sender. До потенциального POST beginSend атомарно фиксирует sendStartedAt и разрешает это не более одного раза в поколении. Guard требует ACTIVE, предшествующую сохранённую сверку absent/incomplete, PREPARED intent с неизменным payload, совпадающий актуальный inbox/configurationVersion, будущий старт, отсутствие сохранённой связи с CRM, lastSuccessfulReadAt не старше 90 секунд и единственный UID среди всех присутствующих сырых ресурсов. Результат POST сохраняется отдельно, известный ID не может заменяться; затем выполняется новая сверка журнала. Отсутствие sendResult после sendStartedAt — неизвестный результат, а не доказательство неотправки.

Локальный guard дополнен обязательным live CalDAV подтверждением, описанным ниже. Вместе они не образуют атомарную транзакцию с CRM. Управляемая активация и production sender описаны ниже. Перед живым включением остаётся проверка установленного приложения на стенде; UI/review и правила обработки конфликтов после отправки ещё не завершены. Сквозная отправляющая ветка проверена на mock API.

Сверка может выполняться даже для intent в NEEDS_REVIEW после изменения источника: это позволяет выяснить результат прежней команды, не разрешая новый POST. CONFIRMED относится к выполнению создания, не синхронизации расписания. Сама сверка ещё не означает APPLIED: при подтверждённом snapshot финализатор отдельно связывает UID и инициализирует общую базу, как описано ниже.

При чтении execution/attempt всегда ограничивайте запрос workspaceId и connectionId. В attempt сохранены статусы сверки и ID, а не raw HTTP ответы/токены. Нужны те же права доступа и резервное копирование, что остальной сервисной БД. Миграция имеет down; откат удалит историю попыток и подтверждений, поэтому перед откатом необходима сохранённая копия этих данных.

## Проверка текущего ресурса через CalDAV перед POST

Восьмая миграция добавляет liveSourceCheck / liveSourceCheckedAt в историю попытки. Флаг `CALENDAR_LIVE_SOURCE_CHECK_ENABLED=true` требует включённого CALENDAR_CREATION_RECOVERY_ENABLED и ключа расшифрования credentials календаря. По умолчанию false. Сам по себе он разрешает только GET к Яндексу; создание в CRM требует дополнительного send flag и активации. `/healthz` сообщает calendarLiveSourceCheckEnabled. Пустая БД при включении не вызывает внешних запросов.

Для absent/incomplete результата CRM worker читает исходный ресурс через существующий authenticated Yandex transport. URL берётся из актуального source intent и проверяется как непосредственный дочерний ресурс выбранного календаря. Credentials открываются только после проверки scope/configurationVersion/state/lease и не входят в результат проверки. Запрос GET содержит If-Match с сильным ETag, Cache-Control=no-cache, запрещает redirects, ограничивает ответ 2 MiB и использует сетевой timeout 15 секунд.

200 подтверждается только при том же ETag, Content-Type text/calendar и совпадающем SHA-256 содержимого. Для сравнения допускается нормализация только переводов строк CRLF/LF: XML calendar-data в REPORT и исходный GET могут различаться этим представлением. Остальные изменения, даже при прежнем ETag, отклоняются. Невалидный UTF-8 и oversized body не принимаются. 404/410/412 означают changed, 401/403 — ошибку доступа, 429/5xx/сеть — временную недоступность. Проверка не выполняет PUT/DELETE.

После GET результат сохраняется только если версия ресурса, захваченная **до** запроса, всё ещё актуальна; совпадения ETag/hash недостаточно при смене resourceVersion. Proof содержит resourceId/version/URL/ETag/hash и время завершения проверки, без календарного текста или credentials. Если запись ждёт блокировки БД, её timestamp не обновляется до времени commit. Пауза, смена конфигурации и истёкший lease запрещают сохранение.

Будущий отправляющий worker обязан выполнить live guard, затем beginSend. SQL beginSend требует verified proof текущего поколения не старше 10 секунд с точным resourceId/version/URL/ETag/hash; одной недавней фоновой загрузки уже недостаточно. Новый source, истечение времени и повторная попытка требуют нового GET. Changed/invalid-source приводят к NEEDS_REVIEW, недоступность — к RETRY; POST не выполняется. При read-only режиме положительная проверка сохраняется, а absent/incomplete остаётся ожидающим следующей сверки.

Проверка одного ресурса не подтверждает отсутствие новых дубликатов UID в ещё не опрошенной коллекции. Полный inventory и локальная проверка UID остаются отдельными проверками. Между GET и POST событие всё ещё может измениться: CalDAV и CRM не имеют общей транзакции. Последующий poll должен выявлять такие расхождения и запускать conflict/review flow. Наличие proof не даёт разрешения записывать в CRM без ACTIVE и остальных проверок.

Transport и сквозной путь encrypted credentials → условный GET → сохранённый proof проверены управляемыми ответами. Настоящие Яндекс credentials не использовались. Проверка metadata-контракта и управляемая активация описаны ниже. Полная проверка живого стенда, UI/review flow и финализация UID-связи/базы merge описана ниже; двусторонние изменения расписания остаются отдельным этапом.

## Проверка CRM, активация и включение создания

Девятая миграция добавляет calendarActivation и capability proof в attempt. Проверка через публичный API сверена с локальными Twenty resolvers/DTO: `currentWorkspace`, `objects`, `fieldsList`, `indexMetadataList/indexFieldMetadataList`, `findManyLogicFunctions`. Внутренние классы Twenty не импортируются.

```bash
node --env-file=.env dist/check-crm.js
```

Проверка не создаёт тестовую тренировку. Она выполняет GraphQL **query** через POST `/metadata` и два GET к `/rest/classSessions` / `/rest/studioEvents` с заведомо отсутствующими ключами. Проверяются workspace токена, universalIdentifier объектов и recordingKey, активные поля/типы, принадлежность объектов и команды одному приложению, единственная команда с требуемым universalIdentifier и её authenticated POST route. Уникальный индекс должен состоять ровно из recordingKey, без subField и partial predicate. Partial GraphQL errors, неправильные фильтры, неполные страницы и несовместимая схема не дают ready.

Это проверка **объявленного metadata-контракта и доступности чтения**, не тест бизнес-поведения обработчика и не прямое исследование физического индекса PostgreSQL CRM. Изолированный API-ключ может иметь права чтения без права выполнения команды: отказ при реальном POST останавливает выполнение. До живого включения установите проверенную версию katfit-studio и проверьте её на тестовом календаре/стенде. Совместимость с конкретным развёрнутым экземпляром в этой разработке не проверялась.

Readiness привязан SHA-256 fingerprint к origin CRM, workspace и API-токену, не сохраняя токен. Evidence содержит IDs объектов, индекса и команды, applicationId и command.updatedAt. Для активации он должен быть не старше 60 секунд.

Порядок включения создания одиночных будущих тренировок:

1. Применить десять миграций собственной БД. Сохранить PREVIEW подключение и включить polling/preview/CRM lookup/create preparation. Для непрерывного потока нужны все эти workers и recovery/live-check; переменные описаны выше.
2. Проверить текущие preview и READY/NEEDS_REVIEW. Активация требует свежий полный снимок (до 90 секунд), подготовленные актуальные ресурсы и отсутствие текущих NEEDS_REVIEW.
3. Выполнить check-crm и проверить установленное приложение на стенде. В .env задать CALENDAR_EXPECTED_CONFIGURATION_VERSION равной текущей configurationVersion подключения.
4. Выполнить операторскую активацию:

```bash
node --env-file=.env dist/activate.js
```

Команда заново проверяет capabilities и в одной транзакции сохраняет receipt и переводит PREVIEW → ACTIVE с compare-and-set ожидаемой версии. configurationVersion **не меняется**: подтверждается именно подготовленная конфигурация и сохраняются frozen-команды. Повтор активации той же версии/контракта идемпотентен. Другой токен/контракт, PAUSED/DISCONNECTED и изменившаяся версия не принимаются.

5. Только после проверки и активации установить `CALENDAR_CREATE_SEND_ENABLED=true` и перезапустить сервис. Это явное включение **создания новых занятий в CRM**. Требуются одновременно CALENDAR_CREATION_RECOVERY_ENABLED=true, CALENDAR_LIVE_SOURCE_CHECK_ENABLED=true и ключ расшифрования. По умолчанию send flag false. В PREVIEW даже worker с send flag остаётся read-only.

Перед каждым потенциальным POST worker проверяет активный receipt и заново читает metadata/REST capabilities; его IDs, command.updatedAt и binding должны совпадать с активацией. Proof сохраняется в attempt и действует 60 секунд. Затем выполняется live CalDAV GET и локальный guard. SQL beginSend также проверяет activation/capability proof в production store и требует минимум 50 секунд оставшегося lease для POST и завершающей сверки. При несоответствии нет отправки; временная недоступность откладывает попытку. Изменение приложения требует review и повторного управляемого flow, а не молчаливого принятия новой команды.

При подтверждённом создании формируется только PLANNED без участников; посещения/списания не создаются. Проверка после POST подтверждает SESSION_CREATED, а перезапуск не отправляет CONFIRMED повторно. После подтверждённого создания выполняется финализация UID-связи и начальной общей базы; соответствующая версия inbox получает APPLIED. Обогащение описания подключается отдельными флагами ниже. Полный двусторонний sync не считается готовым.

Для остановки новых действий используйте операторскую паузу с текущей ожидаемой configurationVersion:

```bash
node --env-file=.env dist/pause.js
```

Для pause нужны только CALENDAR_DATABASE_URL, TWENTY_WORKSPACE_ID, CALENDAR_CONNECTION_ID и CALENDAR_EXPECTED_CONFIGURATION_VERSION. API-токен и encryption key не нужны. Пауза увеличивает configurationVersion, инвалидирует activation и прежние leases/proofs. Уже отправленный внешний HTTP-запрос она не отменяет; его результат может потребовать последующей сверки. Возобновление после PAUSED и review/requeue пока не имеют готового операторского flow; повтор activate для PAUSED запрещён. Не меняйте состояние напрямую SQL для обхода проверок.

Health показывает конфигурационные флаги calendarCreateSendEnabled / calendarLiveSourceCheckEnabled / calendarCreationRecoveryEnabled; они не доказывают активацию конкретного подключения или доступность его API. synchronizationEnabled остаётся false, поскольку обновление/отмена/обратная синхронизация ещё не завершены.

Сквозной тест production factory использует mock CRM/CalDAV: activation → metadata/read probes → live If-Match GET → ровно один POST → сверка журнала → CONFIRMED → idle при повторе. Операторские check-crm/activate/repeat/pause проверены отдельными Node-процессами с временной БД и локальным mock API. В реальном окружении ничего не активировано и CALENDAR_CREATE_SEND_ENABLED не включался.

## Финализация UID и обратное обновление описания

Десятая миграция добавляет commonBase/baseResourceVersion/baseEtag к UID-связи, состояние/lease финализации к execution и календарную очередь обновления описаний calendarDescriptionRefresh. Ядро, таблицы и образ Twenty не меняются.

После подтверждённого SESSION_CREATED inspector возвращает также прочитанный snapshot занятия. В той же транзакции, что завершает creation execution, финализатор:

- проверяет известный classSessionId, recordingKey, исходный resourceId и единственность UID среди присутствующих ресурсов;
- сохраняет `(workspace, connection, UID, single) → classSessionId`, не заменяя уже существующую другую связь;
- сравнивает текущее локальное событие, неизменяемую команду и CRM snapshot по имени/интервалу/формату/вместимости;
- при совпадении сохраняет начальную общую базу имени и интервала, помечает соответствующую текущую UPSERT-версию inbox APPLIED, завершает её reconciliation как LINKED и создаёт локальное задание обогащения;
- при расхождении сохраняет доказанную идентичность, но оставляет commonBase пустой и ставит finalizationState=NEEDS_REVIEW. История/расписание не перезаписываются.

CONFIRMED execution подтверждает создание, finalizationState=LINKED — завершённую привязку. Это разные состояния. Общая база отражает согласованные наблюдения и не гарантирует распределённую атомарность календаря и CRM. Новая внешняя правка поступает новой версией inbox. Ошибка сохранения базы откатывает link/inbox/job вместе. Восстановление ранее подтверждённых executions без snapshot выполняет отдельный read-only финализатор, автоматически запускаемый с CALENDAR_CREATION_RECOVERY_ENABLED; сначала он заново читает занятие из CRM.

Новые флаги (оба по умолчанию false):

```text
CALENDAR_DESCRIPTION_PREPARATION_ENABLED=true
CALENDAR_EXPORT_SEND_ENABLED=false
```

Preparation раз в 60 секунд получает полный список бронирований конкретного будущего связанного занятия через публичную GraphQL query `/graphql` и готовит неизменяемую EXPORT_EVENT операцию в собственной БД. Включение этого флага само по себе не изменяет календарь. BOOKED и ATTENDED включаются в список, отмены/неявки исключаются. Имя и фамилия берутся из `person.name.firstName/lastName` с сохранением написания; клиентские ID используются для различения людей, но не публикуются в тексте. Одноимённые разные клиенты не объединяются. Пустое имя, потерянная person relation, дубли активного клиента, неизвестный статус, GraphQL errors, неверный session filter или hasNextPage блокируют обновление, а не очищают список. Предел — 1000 бронирований в полном ответе и 100 активных участников; пагинация сверх этого пока требует review.

В исходном VEVENT меняются только DESCRIPTION и X-KATFIT-SESSION-ID. Служебный блок содержит ID занятия и имена:

```text
--- KATFIT:GENERATED:BEGIN ---
Тренировка CRM: <classSessionId>
Участники (2):
- Анна Иванова
- Анна Иванова
--- KATFIT:GENERATED:END ---
```

UID, пользовательские комментарии/KATFIT-метаданные, DTSTART/DTEND, SUMMARY, ATTENDEE, alarms и произвольные свойства сохраняются. Приглашения не отправляются и адреса клиентов не добавляются в ATTENDEE. Уже существующий другой X-KATFIT-SESSION-ID и неоднозначные маркеры требуют проверки. Сериализация выполняется iCalendar-библиотекой; формат folding/переводов строк может нормализоваться. Повтор с теми же участниками не добавляет второй блок.

Для реальной публикации в **выбранный закрытый календарь** дополнительно установите `CALENDAR_EXPORT_SEND_ENABLED=true` и перезапустите сервис. Требуются preparation, encryption key, соответствующие API credentials и активный receipt той же конфигурации/binding. Создание новых занятий CALENDAR_CREATE_SEND_ENABLED и обратный PUT — независимые разрешения. В PREVIEW publisher не забирает задания; пауза/ротация/configurationVersion запрещают новые записи. Для постоянной работы нужен polling: он обновляет локальные ETags после успешного PUT.

Путь публикации: проверить ACTIVE/receipt → заново прочитать занятие и roster из CRM → GET текущего события → сверить UID/расписание/параметры и заново вычислить допустимый patch → повторно проверить локальный scope/state/lease → PUT с If-Match → GET для подтверждения. Ресурс должен оставаться текущей связанной версией и принадлежать выбранной коллекции. Поддерживаются непрозрачные и корректно percent-encoded имена ресурса; расширение .ics в URL не обязательно. Slash/backslash, traversal, неправильные/double encodings и внешние origins не допускаются.

Изменение roster до отправки делает draft SUPERSEDED. Правка календаря/412 даёт CONFLICT без перезаписи. PUT с потерянным ответом требует последующего чтения: если желаемый результат уже присутствует, операция завершается без второго PUT; неизвестный результат сохраняется RETRY/requiresReconciliation. Подтверждённые записи не обновляют локальный ресурс оптимистически — его перечитывает обычный poller. Отметка SUCCEEDED означает подтверждение прочитанного результата, не гарантию отсутствия последующих изменений.

Подготовка outbox и подтверждение задания транзакционны. Обработка разных action использует общую очередь с одним RUNNING на подключение; export worker не перехватывает IMPORT_EVENT. Lease/поколение и повторная проверка перед PUT не заменяют If-Match и не отменяют HTTP-запрос, уже отправленный перед паузой.

Пока это создание одиночных будущих занятий и обогащение их описания. Полные переносы/отмены в обе стороны, серии, ручное сопоставление произвольных старых занятий, review/resume UI и уведомления ещё не завершены. Существующие связи без подтверждённого creation/commonBase не начинают автоматически экспортировать клиентские данные. synchronizationEnabled остаётся false; health отдельно показывает calendarDescriptionPreparationEnabled и calendarExportSendEnabled.

В реальном окружении флаги отправки не включались и записи не выполнялись. Сквозные проверки используют временную PostgreSQL и mock API, включая GET→If-Match PUT→GET, конфликт комментария, одноимённых клиентов, сбой roster reader, атомарные откаты и потерянный ответ без повторного PUT.

## Предварительный просмотр импорта

Команда `preview` читает локальный `.ics`, разбирает одиночное событие и выводит кандидата без записи в БД, CRM или календарь. UID сохраняется; ключ создания зависит от workspace, подключения и UID, поэтому перенос времени/переименование не меняют его. Подключение должно сохранять прежний ID. Повторное подключение с новым ID потребует восстановления связей до разрешения автоматического импорта.

```bash
# Переменные задаются через окружение или локальный .env:
# CALENDAR_EVENT_FILE=/absolute/path/event.ics
# TWENTY_WORKSPACE_ID=<UUID>
# CALENDAR_CONNECTION_ID=<UUID>
# CALENDAR_DEFAULT_FORMAT=GROUP_REFORMER
# CALENDAR_DEFAULT_CAPACITY=6
node --env-file=.env dist/preview.js
```

Формат и вместимость можно задать в DESCRIPTION отдельным блоком (переносы строк в файле ICS кодируются как `\n`):

```text
KATFIT:
format=MAT_PILATES
capacity=8
```

Явные значения перекрывают defaults. `group` пока требует ручного сопоставления. Генерируемый блок со списком участников не трактуется как инструкции. Прошедшие события, отмены, серии, all-day, неверные даты, неоднозначные часы при переходе DST и время без TZID/Z отправляются в NEEDS_REVIEW. Эта версия CLI не разрешает floating time. Существующие события, ставшие прошедшими, в дальнейшем нужно обрабатывать через сохранённые связи, а не повторный flow создания.

Без CRM-конфигурации результат READY содержит crmLookup=not-configured и не доказывает отсутствие занятия. Для read-only сопоставления задайте вместе `TWENTY_API_URL` (origin CRM) и `TWENTY_API_TOKEN` (ключ того же workspace). HTTPS обязателен; внутренний HTTP допускается только при явном `TWENTY_ALLOW_INSECURE_HTTP=true`. Redirect запрещён, лимит ответа 2 MiB, timeout 15 секунд. Workspace токена должен проверить оператор: локальный workspaceId не меняет область доступа API-ключа.

Lookup использует GET `/rest/classSessions`, фильтр точного recordingKey и limit=2. Поля ответа сверены с объектом приложения katfit-studio (startsAt/endsAt, без несуществующего durationMinutes). Проверяются схема, возвращённые ключи и hasNextPage. CREATE_CANDIDATE означает успешный пустой ответ; EXISTING_SESSION возвращает найденное занятие даже при отличающемся времени. Ошибки доступа, сети, схемы и дубли дают NEEDS_REVIEW, а не предложение создать дубликат. Проверки выполнялись на управляемых ответах; совместимость с развёрнутой CRM ещё нужно подтвердить. Результаты могут содержать название занятия; храните вывод как данные закрытого календаря.

Это предварительный просмотр создания одиночного занятия, не механизм обновления и не разрешение на запись. Фоновая локальная подготовка inbox описана ниже; Фоновое CRM-сопоставление описано ниже; атомарные доменные команды — следующий этап.

## Сохранение выбранного подключения

Сначала примените миграции в собственной БД сервиса. В локальном окружении задайте:

- `CALENDAR_ENCRYPTION_KEY`: отдельный случайный ключ, 64 hex-символа (`openssl rand -hex 32`). Храните его отдельно от резервной копии БД; без ключа сохранённые пароли не восстановить.
- `CALENDAR_ENCRYPTION_KEY_ID`: идентификатор ключа, по умолчанию primary.
- `TWENTY_WORKSPACE_ID`: UUID workspace из CRM, без обращения к его БД.
- `CALENDAR_CONNECTION_ID`: новый UUID, который нужно сохранить и повторно использовать при повторе той же команды.
- `YANDEX_CALDAV_CALENDAR_URL`: точный URL одного из календарей, полученных командой discover.
- Логин и пароль приложения — как для discover; `CALENDAR_TIMEZONE` по умолчанию Europe/Moscow.

```bash
node --env-file=.env dist/migrate.js
node --env-file=.env dist/connect.js
```

Connect заново выполняет discovery и принимает только календарь из ответа аккаунта, затем шифрует пароль и сохраняет PREVIEW. Повтор с тем же ID и теми же параметрами возвращает существующее подключение; повтор ID с изменёнными параметрами отклоняется. Для workspace допускается одно неотключённое подключение. Пароль не передаётся SQL-запросом в открытом виде и не включается в JSON результата. Это операторский CLI с доступом к конфигурации сервиса; браузерная авторизация ещё не реализована.

Ротация пароля поддержана хранилищем, но отдельный CLI/UI ещё не добавлен. Cipher поддерживает чтение старых key IDs при наличии keyring; CLI пока загружает один ключ. Не меняйте ключ в окружении без отдельной процедуры перешифрования и сохранения старого ключа. Pause/disconnect пока меняют только сохранённую конфигурацию: проверка состояния и версии непосредственно перед каждым внешним действием будет добавлена при реализации worker. Автоматической активации или возобновления здесь нет.

## Связь с CRM

Доменные объекты и команды находятся в приложении `katfit-studio`, устанавливаемом штатными средствами Twenty. Сервис будет обращаться к разрешённым HTTP/API-командам с отдельным workspace-scoped ключом. Прямые SQL-записи в CRM и вызов внутренних классов Twenty запрещены архитектурой.

Атомарность доменных изменений через поддерживаемый API ещё должна быть доказана; до решения этого пункта автоматические изменения занятий и отмены с финансовыми последствиями не включаются. Доступность API не равна гарантии compare-and-set.

Архитектура и оставшийся план находятся в `Docs/studio-yandex-caldav-implementation.ru.md` и `Docs/studio-yandex-caldav-implementation-plan.ru.md` основного репозитория.

### Schedule merge preparation

`planCalendarSchedule` compares the agreed `commonBase`, the current CRM session
and the current CalDAV resource. It merges name and the whole time interval
independently, returning review for conflicting transfers, changed identity,
format/capacity changes, non-editable statuses and past sessions. CRM timestamps
have no display timezone; the agreed base supplies it. The returned `expectedCrm`
is a precondition for a future conditional update, not permission for a plain
read-then-PATCH sequence.

`renderCalendarSchedule` prepares SUMMARY/DTSTART/DTEND while preserving UID,
description, attendees, alarms and other properties. DURATION is replaced by an
explicit DTEND. The result must round-trip through the strict event parser;
ambiguous DST times require review.

These functions are used by the opt-in schedule workers described below.
Description publication remains independent. A normal `updateClassSession` after
a read cannot prevent overwriting an intervening user edit; schedule writes use
the filtered public mutation instead.

### Conditional CRM transfer adapter

`createCalendarScheduleUpdater` uses the public GraphQL `updateClassSessions`
mutation with a filter on ID, recordingKey, previous name, both timestamps,
format, capacity and editable status. It writes only name/startsAt/endsAt.
The local Twenty implementation carries these predicates into the SQL UPDATE;
no core patch or new CRM logic function is required. Zero returned records is a
conflict. The adapter validates the exact returned identity and schedule and
never retries a request itself.

`recoverCalendarScheduleUpdate` reads before sending, recognizes an already
observed target, refuses an intervening edit and checks authorization immediately
before sending. It reads again after success or an uncertain response. This
confirms observed state, not ownership of a historical write or a studio audit
event. A retry must receive the same persisted immutable command. The recovery
function itself has no persistence; the schedule worker supplies the frozen
command from the durable operation payload.
The timestamp cutoff uses the service clock at dispatch; staging must verify
clock skew, the installed API schema, permissions and concurrent-update behavior
before any live enablement.

Neither adapter is enabled by existing creation/description flags. Schedule
workers require their own explicit flags, described below.


## Двусторонние переносы связанных одиночных занятий

Примените 11-ю миграцию собственной схемы сервиса. Она добавляет к связи
`nextScheduleCheckAt` и `scheduleReviewReason`; таблицы Twenty не затрагиваются.

- `CALENDAR_SCHEDULE_PREPARATION_ENABLED=true` включает опрос связанных занятий
  через CRM API и подготовку неизменяемых операций `RECONCILE_RESOURCE` с
  `kind=SYNC_SCHEDULE`. Работает в PREVIEW/ACTIVE; отправки нет.
- `CALENDAR_SCHEDULE_SEND_ENABLED=true` включает выполнение. Требует подготовки,
  `CALENDAR_POLLING_ENABLED=true`, ключа шифрования и CRM-конфигурации. Флаги по
  умолчанию false; Compose передаёт их явно. Отправка возможна только в ACTIVE
  с действующей квитанцией активации для тех же workspace/connection/config/token.

Подготовка проверяет одну связь за цикл, повторный опрос — через 60 секунд.
Обрабатываются только связанные события с общей базой. Изменения названия и
интервала сливаются независимо, конфликтующие переносы требуют разбора.
Формат, вместимость, записи, посещения и финансы не изменяются.

Операция хранит исходный CalDAV ресурс, ETag, общую базу, ожидаемую CRM и целевое
расписание. Ключ — SHA-256 канонического payload; существующую команду нельзя
перезаписать. До завершения текущего намерения новое для того же UID не готовится.
Обработчик использует общую очередь с 300-секундным lease и fencing; одновременно
для подключения работает одна операция очереди, включая публикацию описания.

Перед CRM-записью проверяются ACTIVE/config/binding/lease, единственность UID в
снимке и свежесть полного чтения (90 секунд), затем выполняется актуальный GET
CalDAV. Допустим только сохранённый исходник с прежним ETag либо уже достигнутая
цель. CRM обновляется условной мутацией с проверкой ожидаемых полей. Перед PUT
повторно проверяются CRM и контекст; PUT использует If-Match. Неопределённые
ответы восстанавливаются чтением, уже достигнутая цель повторно не записывается.

Успех операции и commonBase фиксируются одной локальной транзакцией только
после чтения обеих сторон и после того, как обычный poller сохранил точные
подтверждённые содержимое и ETag. До этого операция RETRY, база остаётся старой.
Poller остаётся единственным владельцем calendarResource; нет оптимистической
подмены снимка после PUT. При новой правке возникает CONFLICT и
scheduleReviewReason блокирует новые намерения этой связи. Автоматического
разрешения конфликта/отката CRM после частичного переноса нет.

Ограничения: это последовательный обмен двух систем, не распределённая
транзакция. Правка после финального чтения обнаруживается следующим циклом.
Пауза не отменяет запрос, уже переданный сети. Сравнение тела допускает только
разницу переводов строк; нормализация свойств сервером потребует разбора.
Квитанция активации проверяет существующий контракт создания, а не доказывает
поддержку условных переносов установленной версией CRM. До включения отправки
на реальных данных обязательно проверить GraphQL-схему, права, конкурентный
UPDATE и поведение Яндекса на отдельном стенде.

health возвращает calendarSchedulePreparationEnabled и calendarScheduleSendEnabled
как признаки конфигурации, не готовности конкретного подключения.
synchronizationEnabled остаётся false: отмены, серии и операторский flow
восстановления подключения ещё не закончены; локальный разбор конфликтов расписания описан ниже.

## Операторский разбор конфликтов расписания

Добавлена локальная CLI-команда `review-schedule`; HTTP endpoint и UI не добавлялись.
Новая миграция не нужна: решение хранится в `resolution` неизменяемого payload
очередной операции. Предыдущие CONFLICT-операции и их payload сохраняются.

Команды запускаются из директории сервиса с переменными собственного подключения:
`CALENDAR_DATABASE_URL`, `TWENTY_WORKSPACE_ID`, `CALENDAR_CONNECTION_ID`.
Окружение `.env` не загружается автоматически; для него используйте
`node --env-file=.env dist/review-schedule.js` вместо npm-команды.

1. Получить первые 100 конфликтующих UID без сетевых запросов и без ключа шифрования:

   ```bash
   CALENDAR_REVIEW_MODE=list npm run review-schedule
   ```

2. Прочитать один конфликт, текущую CRM и актуальный ресурс CalDAV:

   ```bash
   CALENDAR_REVIEW_MODE=inspect CALENDAR_REVIEW_UID='UID из списка' npm run review-schedule
   ```

   Для inspect/resolve также нужны `TWENTY_API_URL`, `TWENTY_API_TOKEN`,
   `CALENDAR_ENCRYPTION_KEY` и соответствующий key ID. Результат содержит причину,
   прежнюю базу, варианты `crm` и `calendar`, состояние подключения,
   `reviewToken` и `expiresAt`. Пароли, ciphertext и исходное описание календаря
   в отчёт не попадают. Если GET не совпал со снимком БД, сначала дождитесь poller.

3. В течение двух минут выбрать расписание одной стороны целиком:

   ```bash
   CALENDAR_REVIEW_MODE=resolve CALENDAR_REVIEW_UID='тот же UID' \
     CALENDAR_REVIEW_CHOICE=crm CALENDAR_REVIEW_TOKEN='токен из inspect' \
     npm run review-schedule
   ```

   `crm` выбирает название/интервал CRM; `calendar` — название/интервал календаря.
   Команда повторно читает обе стороны и сравнивает отпечаток с просмотренным.
   Новая правка, другая версия подключения, истечение срока или неоднозначный UID
   требуют нового inspect. Проверка срока повторяется в транзакции после ожидания
   блокировки. Сами часы сервиса и PostgreSQL должны быть синхронизированы.

`resolve` не отправляет изменения наружу. В одной транзакции создаётся новая
операция, неисполненные PENDING/RETRY намерения этого UID становятся SUPERSEDED,
а блокировка связи снимается. Общая база не меняется до обычного подтверждения
обеих сторон воркером. Если для подключения есть RUNNING-операция, возвращается
busy, включая истёкший lease: оператор не отменяет потенциально отправленный
сетевой запрос. Для очереди нужны обычные schedule-флаги и действующая ACTIVE
активация; в PREVIEW решение только сохраняется.

Повтор resolve с тем же токеном и выбором возвращает существующую операцию и её
текущее состояние, даже если срок токена уже истёк; новая операция не создаётся.
Другой выбор с использованным токеном отвергается. Конкурирующие решения проходят
через общий lock подключения; применяется одно. Правки после постановки решения
в очередь всё равно проверяются обычными CRM CAS и CalDAV If-Match.

Токен — отпечаток для защиты от устаревшего решения, не механизм авторизации.
CLI предназначена для доверенного оператора с доступом к БД сервиса и ключам;
пользовательский RBAC и идентификация автора решения пока не реализованы.
Просмотр PAUSED допускается, применение решения — только PREVIEW/ACTIVE.
Это разбор конфликтов расписания связанных будущих одиночных занятий с commonBase,
а не восстановление AUTH_REQUIRED/ERROR/PAUSED подключения, конфликта создания,
смены формата/вместимости, удалений или серий. Эти случаи команда не разблокирует.

## Запросы на отмену и подтверждение удаления

Миграция 12 добавляет `calendarCancellationReview` и `nextCancellationCheckAt`
в собственную схему сервиса. `CALENDAR_CANCELLATION_REVIEW_ENABLED=true` включает
обработчик запросов на отмену в PREVIEW/ACTIVE. Нужны polling, CRM read API и ключ
шифрования CalDAV; по умолчанию флаг false. Внешние мутации этим флагом не включаются.
health показывает calendarCancellationReviewEnabled и всегда
calendarCancellationSendEnabled=false.

Поддерживаются два сигнала для уже связанного одиночного занятия:

- отсутствие ресурса: минимум два успешных полных inventory, не менее 60 секунд
  после первого MISSING_CANDIDATE и актуальный GET по прежнему href с 404/410;
- явный STATUS:CANCELLED: строгая проверка одиночного VEVENT без серии и актуальный
  GET с теми же телом и ETag, что сохранены poller.

Перемещение UID на другой href, дубликаты, неизвестные UID, неподдерживаемое событие,
401/403, сетевые ошибки и несогласованные снимки не становятся подтверждённой
отменой. Изменение поколения/конфигурации/версии ресурса во время проверки отвергает
сохранение результата. Данные снимка должны быть не старше 90 секунд.

Запрос имеет состояние AWAITING_CONFIRMATION или NEEDS_REVIEW; `calendarConfirmed`
подтверждает только сигнал календаря. Дополнительно читаются текущая CRM-сессия и
полная страница её записей (до 1000). Сохраняются количества записей, активных и
посещённых, признаки ожидаемой/полученной оплаты и списания посещения. Это снимок
полей бронирований, не сверка платежей или финансового ledger. Неполный/ошибочный
ответ никогда не трактуется как пустой список.

В одной транзакции сохраняется запрос и ставится блокировка автоматического
расписания `CALENDAR_CANCELLATION_REQUIRES_REVIEW` без затирания другой причины.
Повторные проверки той же версии обновляют снимок запроса, не создавая дубликатов.
Новые версии оставляют прежние запросы SUPERSEDED. Если событие снова появляется
как валидное одиночное с тем же UID без отмены, старый запрос становится SUPERSEDED;
снимается только собственная блокировка отмены.

Просмотр первых 100 текущих запросов (без сети, API-токена и ключа шифрования):

```bash
npm run review-cancellations
# С явной загрузкой .env:
node --env-file=.env dist/review-cancellations.js
```

Нужны только CALENDAR_DATABASE_URL, TWENTY_WORKSPACE_ID и CALENDAR_CONNECTION_ID.
Вывод содержит признаки риска и причину разбора, без имён клиентов и сырых описаний.
Он не является командой исполнения отмены.

**Автоматической отмены в CRM пока нет, включая занятия без записей.** Текущие
доменные команды отменяют отдельные бронирования, резервы и ожидаемые оплаты
несколькими вызовами. Между проверкой пустого занятия и сменой статуса может
появиться новая запись. Нужна отдельная доказанная доменная операция отмены занятия
с защитой от конкурентного бронирования и восстановлением частичного выполнения;
до её появления worker не меняет статус, бронирования, оплаты, посещения, остатки
пакетов и не удаляет события. Оператор разбирает запрос в штатном интерфейсе CRM.
Наблюдение результата ручной отмены описано ниже.

## Наблюдение результата штатной отмены

Миграция 13 добавляет initialBookingIds, seenBookingIds, outcomeObservedAt и таблицу
calendarCancellationObservation. Существующий cancellation-review worker продолжает
работать под тем же флагом; внешних мутаций по-прежнему нет.

При первом успешном чтении до отмены сохраняется исходный список ID броней.
Дополнительно накапливаются все замеченные ID, включая поздние записи. Эти наборы
не заменяются текущим пустым списком. Если замеченная бронь исчезла, запрос остаётся
NEEDS_REVIEW с CANCELLATION_BOOKING_HISTORY_MISSING. Сервис может проверить только
брони, попавшие в его снимки; запись и удаление полностью между опросами этим не
доказываются.

Если оператор отменил занятие штатными средствами и сервис наблюдает
CANCELLED_BY_STUDIO, сохранённую пустую исходную историю и полный пустой текущий
список, запрос получает CRM_CANCELLED_OBSERVED. Это отметка наблюдаемого состояния,
не атомарная гарантия отсутствия будущей записи. Мониторинг продолжается; новая
активная бронь, платёжный/посещенческий признак или ошибка проверки возвращают
запрос на разбор. Блокировка автоматического расписания сохраняется.

Для занятий с бронями отсутствие активных флагов не доказывает согласованность
резервов пакета/платежей. Такие запросы остаются на финансовом разборе
CRM_CANCELLED_FINANCIAL_RECONCILIATION_REQUIRED. Старые запросы без достоверной
исходной истории также не получают автоматическую отметку результата.

Смена состояния и запись наблюдения сохраняются одной транзакцией. Неизменный
снимок не дублирует наблюдение; последующие переходы сохраняют отдельные записи.
Просмотр последних 100 наблюдений конкретного запроса в том же scope:

```bash
CALENDAR_CANCELLATION_REVIEW_ID='UUID запроса из списка' npm run review-cancellations
```

Журнал добавляется сервисом; это не CRM-аудит и не подтверждение исполнения
финансовой операции. Доступно явное исполнение отмены оператором через `execute-cancellation` (описано ниже). Фоновая автоматическая отмена выключена.
Требования к ней и к единой защите всех writers приведены в
`Docs/studio-cancellation-execution-contract.ru.md` основного репозитория.

### Явное исполнение отмены оператором

`npm run execute-cancellation` работает только с одним сохранённым запросом
`CALENDAR_CANCELLATION_REVIEW_ID` и ожидаемой версией
`CALENDAR_EXPECTED_CONFIGURATION_VERSION`. Укажите обычные параметры подключения
к собственной БД сервиса, CRM и ключ шифрования CalDAV.

Сначала выполните `CALENDAR_CANCELLATION_EXECUTION_MODE=prepare npm run execute-cancellation`.
Команда проверит активную конфигурацию и её привязку к CRM, метаданные guarded
команд, свежий полный инвентарь, живой CalDAV-ресурс и исходный список броней.
Результат `prepared` содержит неизменяемый запрос с ID занятия, точным списком
броней, временем отмены и ключом идемпотентности. Изменившийся список, оплаченные
или проведённые записи и неоднозначная история требуют отдельного разбора.

После проверки запроса явно выполните
`CALENDAR_CANCELLATION_EXECUTION_MODE=execute CALENDAR_CANCELLATION_SEND_ENABLED=true npm run execute-cancellation`.
Флаг по умолчанию выключен; фоновый обработчик автоматически отмены не исполняет.
Перед отправкой повторяются проверки, затем атомарно сохраняется `SENDING`.
Отправляется один POST `/s/studio/sessions/cancel`; успех требует сохранённого
`SUCCEEDED` в журнале CRM с тем же запросом, совпадающего списка броней и повторного
чтения отменённого занятия без активных, оплаченных или потребляющих визит броней.
Сами брони, платежи и проводки сохраняются. Приложение CRM освобождает резервы
обычных и split-записей, а неоплаченные разовые записи переводит в `WAIVED`.

После потери ответа повтор CLI только читает журнал и итог CRM. Второй POST
автоматически не отправляется. Неподтверждённое частичное исполнение остаётся
`NEEDS_REVIEW`; не удаляйте его запись и не меняйте ключ для обхода блокировки.
Пауза подключения, новый инвентарь, изменившаяся версия ресурса или конфигурации
перед началом отправки запрещают исполнение. Уже отправленный HTTP-запрос пауза
отозвать не может.

Перед использованием требуется установить новую версию пользовательского
приложения и ограничить прямое изменение занятий/броней/платежей для участников.
Проверка метаданных подтверждает объявленные поля и маршруты; стендовая проверка
эффективных прав и поведения установленного приложения остаётся обязательной.
