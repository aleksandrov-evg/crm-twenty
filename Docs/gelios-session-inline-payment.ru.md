# Разовая оплата из формы тренировки

25 октября 2026. Реализовано локально в katfit-studio и внешнем UI/API KateFitNotes; на stage и production не применялось.

В форме создания тренировки доступны все клиенты. Клиент с подходящим пакетом добавляется с этим пакетом. У клиента без пакета после добавления в список появляется кнопка «Создать оплату». В одной группе можно совмещать оба способа; персональная тренировка по-прежнему рассчитана на одного человека. Сплиты и внесение участников в уже идущую тренировку остаются отдельными сценариями.

Кнопка открывает форму разовой услуги внутри окна тренировки. Формат, длительность и московский день берутся из занятия. Для группы используются активные SINGLE-продукты; для персональной — PERSONAL с одним посещением. Версия продукта должна действовать в выбранный день.

- Будущая тренировка: создаётся EXPECTED, без paidAt и подтверждения получения денег.
- Прошедшая: после явного подтверждения получения денег создаётся PAID, с выбранным способом оплаты и paidAt в 00:00 дня занятия по Москве.

Оплата сохраняется сразу, до тренировки. Закрытие формы или удаление человека из черновика не отменяет оплату; интерфейс об этом сообщает. Черновик сохраняет ссылку на оплату в sessionStorage. Потерянный ответ повторяется с прежним ключом; до завершения оплаты изменения формы заблокированы.

POST /studio/sessions/payment создаёт оплату и обязательное событие с UUID оплаты. Контекст клиента, продукта, начала, длительности, формата и исходного статуса хранится в nullable TEXT studioPayments.sessionPaymentContext. Повтор с другими параметрами отклоняется. Для долгов добавлен тип события PAYMENT_EXPECTED.

sessions/create теперь принимает участника либо {personId,membershipId}, либо {personId,productId,paymentId}. Сервер проверяет принадлежность и сохранённые параметры оплаты до создания слота, а затем повторно перед добавлением участника. Изменение времени, даты или формата требует пересмотра оплаты. Уже привязанную оплату нельзя использовать для второй тренировки.

Участники по пакету проходят прежние RESERVE/CONSUME. Разовые получают BOOKED/EXPECTED или ATTENDED/PAID, без операций с посещениями пакета. Все участники оформляются под существующей блокировкой session-participants; при частичном сбое сохраняется NEEDS_REVIEW, повтор не дублирует записи. Оплата связывается с бронированием через штатный externalId pay-as-you-go:<bookingId> для последующих подтверждения долга и отмены.

Для выпуска сначала применить metadata/logic functions CRM (поле sessionPaymentContext, PAYMENT_EXPECTED, новая studio-create-session-payment и обновлённая studio-create-class-session), затем API и UI. Выпуск одного UI недостаточен.

Проверено: модульные тесты CRM, прямой tsgo и oxlint; UI unit/syntax; API-маршруты и аудит. Браузерный тест `npm --prefix ui run test:browser:session-payment` с моками покрывает смешанную группу, персональную оплату задним числом, долг до создания тренировки, потерю ответа/reload/retry и блокировку при изменении даты. Реальные оплаты не создавались.
