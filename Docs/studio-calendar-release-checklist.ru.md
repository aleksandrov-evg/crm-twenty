# Проверка и выпуск интеграции календаря

## Состав поставки

- `services/katfit-calendar-sync`: самостоятельный процесс и собственная схема PostgreSQL `calendar_sync`; CalDAV-транспорт, очередь, сверка и операторские CLI.
- `packages/twenty-apps/internal/katfit-studio`: пользовательское приложение Twenty; команды бронирования, посещения, изменения и отмены занятия, журнал владения.
- Образ и исходники ядра Twenty не изменяются. Для сервиса собирается отдельный образ; приложение устанавливается штатным SDK. Новые поля и индексы относятся к приложению, не к миграциям ядра CRM.

## Порядок выпуска

1. Сохранить резервные копии CRM и базы сервиса. Зафиксировать версию официального образа Twenty и установленную версию приложения.
2. Собрать и проверить приложение локально. Установить обновление приложения на тестовую CRM штатным SDK, проверить наличие метаданных, индексов и маршрутов из manifest.
3. Проверить условные массовые update-запросы установленного API: два конкурирующих владельца получают ровно одного победителя; потерянный ответ восстанавливается чтением; старый владелец не снимает новую блокировку.
4. Проверить права обычных пользователей и ключей: запретить прямое изменение занятий, броней, проводок, платежей, остатков и технических журналов в обход команд. Проверить и GraphQL, и REST, и стандартные формы CRM. Аутентификация HTTP-маршрута сама по себе не доказывает эти права. Локальный `scripts/audit-gateway-permissions.mjs` показывает список проверок, но не может подтвердить права установленной CRM.
5. Развернуть отдельный сервис с выключенными флагами отправки. Выполнить миграции его собственной схемы. Задать ключ шифрования через секрет окружения; не помещать пароль приложения Яндекса в Git или журналы.
6. Подключить закрытый тестовый календарь Яндекса в PREVIEW. Выполнить discovery и проверку CRM capabilities. Проверить ФИО, UID, часовой пояс, создание с телефона и веб-интерфейса, перенос, переименование, повторную доставку и конфликт изменений.
7. По отдельности включать подготовку и отправку создания, обогащения и расписания. После каждого шага проверить журнал операций, свежий снимок CalDAV и итоговое состояние CRM. Совпадения полей недостаточно для подтверждения незавершённой доменной команды.
8. Проверить отмену на пустом занятии, обычных пакетных бронях, split и разовой неоплаченной записи. Оплаченные, проведённые и неоднозначные случаи направляются на ручную сверку. Автоматический фоновый вызов отмены не включается этой поставкой.
9. Выполнить перезапуск процесса и восстановление после сетевого таймаута. Подтверждённая квитанция допускает повтор без новых списаний; EXECUTING/NEEDS_REVIEW не разблокируются по возрасту.

## Обязательные сценарии приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Событие создано в календаре | Одна тренировка в CRM, стабильная связь UID ↔ ID, обогащение календаря после подтверждения |
| Перенос в CRM или календаре | Одинаковое расписание после подтверждённой команды и условного PUT |
| Одновременные несовместимые изменения | Конфликт для оператора; нет молчаливой перезаписи |
| Два занятия используют последний визит пакета | Только один владелец пакета до бизнес-записей |
| Отмена одновременно с записью/посещением/оплатой | Один согласованный владелец; неопределённый результат остаётся на разбор |
| Потерян ответ после записи | Нет повторного списания; подтверждение по журналу либо ручная сверка |
| Чужой/поздний владелец | Не может снять актуальную блокировку |
| Полный снимок CalDAV не получен | Удаление не выводится из неполного списка |
| Повторяющееся событие | Не импортируется как одиночное занятие; серии исключены из версии 1 |

## Откат

Сначала отключить отправку и остановить сервис; сохранить его БД, очередь и журналы. Не удалять поля владения, квитанции и проводки при незавершённых операциях. Не снимать блокировки массовым SQL. Возврат предыдущей версии приложения допустим только после сверки незавершённых владельцев и совместимости метаданных. Простой откат исходников не отменяет уже созданные занятия, списания и внешние CalDAV-записи.

## Граница локальной проверки

Unit-тесты с fake CRM проверяют протокол обработчиков, но не эффективные права и атомарность SQL установленного Twenty. Тесты с временной PostgreSQL проверяют только собственное хранилище сервиса. Реальные учётные данные, установка приложения и изменения рабочего календаря требуют отдельной приёмки по шагам выше.

Подготовленная отмена привязана к исходному расписанию CRM и списку броней.
Перенос или другое изменение занятия после подготовки требует нового разбора;
совпадения только ID занятия недостаточно. Снимок повторно проверяется самой
доменной командой после захвата владения занятием.
