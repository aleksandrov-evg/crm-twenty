# Проверка полноты журналирования CRM — 25 октября 2026

## Результат

Утверждение «абсолютно все действия CRM сохраняются в журнале» не подтверждено.
Проверены исходники Twenty, katfit-studio и операторского API KateFitNotes.
Это локальная проверка кода; конфигурация и доставка событий на работающих
stage/production не проверены, изменения не развёрнуты.

## Что добавлено

`KateFitNotes_telegram/src/Kate_Fit_Notes/api/request_log.py` — ASGI middleware,
регистрируемое в `create_app`. Для каждого HTTP-запроса создаются события
`api_request` с фазами `started`/`finished`, серверным UUID, временем UTC,
методом; в конце — шаблоном маршрута, проверенным пользователем, HTTP-статусом,
длительностью, признаком завершения отправки ответа и типом исключения.
Вход и JWT-проверка задают пользователя только после успешной проверки.
Отмена запроса/исключение также проходят через `finally`; аварийное завершение
процесса может оставить только `started`.

Записи идут в стандартный Python logger `uvicorn.error.request_audit`, наследующий
настройки uvicorn. Для уровней INFO в штатном запуске видны успешные запросы,
для 4xx/5xx используются WARNING, для исключений ERROR. При глобальном уровне
WARNING успешные события будут отфильтрованы: эксплуатационная конфигурация
должна сохранять INFO этого logger. Для запросов без маршрута используется
`UNMATCHED`; маршруты FastAPI могут содержать локальный путь без router prefix.

В обычные ответы добавляется `X-Request-ID`. Ответ на необработанное исключение
формируется внешним ServerErrorMiddleware и может не содержать этот заголовок;
само исключение фиксируется с внутренним request_id.

Тела, query string, произвольные URL, пароли, JWT, API-ключи и текст исключений
не копируются в новые записи. Существующие access/error-логи uvicorn и других
компонентов на предмет персональных данных этой правкой не изменены.
Это технические логи процесса, не новые строки бизнес-журнала CRM и не
надёжная очередь доставки. Общий request_id пока не передаётся в Twenty.

## Условия подтверждения полного покрытия

1. Проверить реально запущенную версию Twenty, `EVENT_SINKS`, доступность ClickHouse
   и наличие сохранённых событий; конфигурация этого checkout может отличаться.
2. Проверить прямое создание, изменение, удаление и восстановление всех используемых
   объектов через UI и API, массовые изменения, расходы, лиды, задачи, настройки,
   права, вход/выход, фоновые задания и календарную синхронизацию.
3. Для каждого изменения проверить автора, источник, время, объект, значения до/после
   и связь с операцией; для отказа — этап и причину. Технический HTTP-статус
   сам по себе не объясняет конкретный бизнес-отказ.
4. Устранить отбрасывание событий при недоступности хранилища: нужна сохраняемая
   очередь/outbox с восстановлением доставки, контролем backlog и сигналом сбоя.
5. Настроить сбор stdout/API/function/server/worker-логов в постоянное хранилище,
   срок хранения, поиск и доступ оператора; проверить перезапуск и пересоздание
   контейнеров. Эти настройки не подтверждены локальными тестами.
6. Проверить защиту журнала от изменения/удаления оператором и исторические пропуски.
7. Только после проверки доставки при сбоях и сверки бизнес-записей с событиями
   считать покрытие подтверждённым для перечисленных сценариев.
