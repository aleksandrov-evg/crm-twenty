# Операторский разбор блокировок и проверка прав KATFIT

## Просмотр журнала

Локальная команда выполняет только GraphQL query. Она не публикует новый HTTP endpoint, не меняет состояние журнала, не освобождает блокировки и не повторяет бизнес-команды.

Из `packages/twenty-apps/internal/katfit-studio`:

```bash
export STUDIO_OPERATOR_CRM_URL=https://crm.example.com
# STUDIO_OPERATOR_API_TOKEN передать через менеджер секретов или окружение.
node --experimental-strip-types --import ./scripts/register-test-hooks.mjs \
  scripts/inspect-session-operation.mjs 'regular-booking:<hash>'
```

Использовать выделенный операторский токен с чтением `studioSessionOperations` и `classSessions`. Команда не нуждается в записи. URL — HTTPS origin без пути, логина и пароля; редиректы запрещены; чтение ограничено 15 секундами и 2 МиБ на запрос. Токен не передавать аргументом командной строки. Вывод содержит персональные данные замороженной команды; хранить его как операторский отчёт CRM.

Результат содержит замороженный request, сохранённый result, состояние операции, состояние занятия и сопоставление владельцев. Значения ownerToken/mutationLock не выводятся; известные токены удаляются также из request/result. `snapshot` — SHA-256 наблюдения, а не разрешение на запись. Журнал, блокировка занятия и все блокировки абонементов из замороженного `membershipIds` читаются дважды; обнаруженная смена возвращает `changed-during-inspection`. Стабильные последовательные чтения не создают транзакционный снимок и не исключают промежуточное изменение с возвратом к прежнему значению.

| Ситуация | Действие |
| --- | --- |
| `SUCCEEDED` с корректным receipt, тот же владелец или блокировка уже снята | Повторить исходную штатную команду с теми же параметрами и idempotencyKey. Её обработчик валидирует конкретный receipt и условно снимает только собственную блокировку. |
| `REJECTED` с корректным receipt и тем же владельцем либо без блокировки | Тот же повтор возвращает сохранённый отказ. Изменённый запрос требует нового ключа после разбора. |
| `EXECUTING`, `CLAIMED`, `NEEDS_REVIEW`, повреждённый receipt | Проверить брони, транзакции, резервы и аудит. Не сбрасывать lock по возрасту, не переводить вручную в SUCCEEDED. |
| Другой владелец, ошибка чтения или изменившийся снимок | Повторить только просмотр; не освобождать чужую блокировку. |

Универсального «продолжить неизвестную операцию» здесь нет. После потери ответа частично выполненная финансовая операция неотличима от выполняющейся без предметной сверки. Эта команда оставляет её заблокированной. Для каждого такого восстановления нужен отдельный доменный доказуемый алгоритм, а не установка статуса оператором.

## Снятие блокировок подтверждённого терминального исполнения

Если исходный HTTP-маршрут недоступен, локальная команда может снять остаточные блокировки **только** уже завершённой операции:

```bash
node --experimental-strip-types --import ./scripts/register-test-hooks.mjs \
  scripts/recover-terminal-session-operation.mjs 'edit-session:<hash>' '<snapshot из свежего просмотра>'
```

Для неё нужен отдельный операторский токен с необходимым правом записи lock-полей. Транспорт команды допускает только условное `mutationLock = null` с точным `id + прежний владелец`; произвольные бизнес-мутации отклоняются локально. Эта команда не публикуется в CRM как общедоступный authenticated route.

Перед первым изменением повторяются двойное чтение и сверка полного fingerprint. Разрешены только `SUCCEEDED`/`REJECTED`, известный prefix и корректная для него квитанция: ID записи/пары/платежа/занятия и счётчик посещений проверяются согласно виду операции. Все ресурсы должны принадлежать тому же исполнению либо уже быть свободными. Сначала освобождаются абонементы, затем занятие; перед каждым шагом проверяется неизменность терминального журнала. Сам журнал, статус занятия, брони и финансы не меняются. Потерянный ответ сверяется чтением; неопределённость останавливает продолжение. Конкурентная смена владельца не перезаписывается.

После частичного освобождения прежний snapshot больше не подходит: выполнить просмотр снова и использовать новый. Любая чужая активная блокировка требует разбора. Старые request без `membershipIds` envelope не содержат доказуемого перечня ресурсов и остаются `legacy-unknown` с ручным разбором. `PURCHASE` и отдельные `purchaseOperationReceipt` не относятся к журналу занятия и этой командой не освобождаются. `CLAIMED`, `EXECUTING`, `NEEDS_REVIEW` команда не восстанавливает и не разблокирует.

## Аудит доступа к gateway

```bash
node scripts/audit-gateway-permissions.mjs
```

Команда читает исходные декларации роли и HTTP-маршрутов, выводит инвентарь маршрутов и признаки обязательной аутентификации. Код выхода **2** означает, что готовность не подтверждена. Проверка намеренно не становится успешной только из-за `isAuthRequired: true`.

Существующая `default-function.role.ts` объявляет глобальное чтение и обновление объектов для приложения. Эти декларации не доказывают, что обычный пользователь или API key лишён прямой записи; аутентификация маршрута не доказывает отдельное разрешение оператора. Локальная проверка не читает назначения ролей установленного workspace и не меняет их.

SDK поддерживает `objectPermissions` и `fieldPermissions` в ролях (`packages/twenty-sdk/src/sdk/define/roles/define-role.ts`), но добавление декларации не назначает пользователей и не отменяет разрешения уже выданных ролей/API keys. Поэтому автоматическое изменение имеющейся роли не выполняется. Его необходимо сверить с реальными объектами, ролями и механизмом выполнения функций установленной версии Twenty.

Минимальная целевая матрица:

| Субъект | Разрешено | Обязательно запретить/проверить |
| --- | --- | --- |
| Обычный сотрудник / клиентский API key | Чтение разрешённых данных; вызов разрешённых команд приложения | Прямые create/update/delete защищённых броней, сессий, абонементов, транзакций и журнала; запись lock-полей |
| Оператор просмотра | Чтение журнала и относящихся к нему данных | Запись журнала/lock; произвольный вызов привилегированных функций |
| Исполнитель приложения | Только необходимые доменные чтения и записи через проверенные обработчики | Глобальная запись посторонних объектов, hard/soft delete финансовой истории |
| Сервис календаря | Разрешённые query и точные команды расписания/отмены | Произвольная запись бронирований, посещений, оплат, lock и журнала |

До включения автоматической отмены на тестовом workspace необходимо получить подтверждение **эффективных** прав каждого реального токена/пользователя:

1. Снять назначения всех ролей и API keys, включая наследование и административные исключения. Сопоставить object/field permissions с установленными universalIdentifier и metadata id.
2. На специально созданных тестовых записях проверить отказ прямых GraphQL **и REST** мутаций защищённых объектов и lock/journal полей обычным пользователем и календарным токеном. Проверить также batch mutation, DELETE, создание и обновление связей. Проверки не выполнять на рабочих данных.
3. Проверить отказ анонимного вызова функций и вызова запрещённых команд каждым субъектом; разрешённый вызов должен исполниться с нужной ролью приложения.
4. Убедиться, что штатный UI и все обработчики изменения защищённых данных используют координацию; прямой доступ администратора считать отдельным операционным исключением, а не конкурентно безопасным API.
5. Сохранить отчёт с workspace id, версией приложения/сервера, идентичностями ролей и токенов без секретов, временем и результатами негативных проверок. Изменение ролей/токенов/метаданных требует новой проверки.

Пока эффективный запрет обхода через прямую API-запись не проверен, блокировка гарантирует взаимное исключение только между участниками, которые соблюдают протокол gateway. Исходный код и локальные тесты не подтверждают эту предпосылку на рабочей CRM.
