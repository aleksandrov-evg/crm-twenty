# Twenty CRM: регламент работы студии

## Назначение

Twenty используется как единое место для работы с потенциальными и действующими клиентами: от первого обращения до продажи, запуска проекта и дальнейшего сопровождения.

CRM хранит коммерческую историю, контакты, договорённости, задачи и общее состояние клиентских проектов. Технические задачи разработки остаются в профильном таск-трекере, а в CRM хранится ссылка на него.

## Основные сущности

| Сущность | Что хранить |
| --- | --- |
| `People` | Заказчиков, лидов, партнёров и другие контактные лица |
| `Companies` | Компании клиентов и партнёров |
| `Opportunities` | Потенциальные сделки и новые проекты |
| `Tasks` | Следующие действия: звонок, встречу, оценку, отправку документов |
| `Notes` | Результаты встреч, требования и зафиксированные договорённости |
| `Projects` | Выигранные и выполняемые клиентские проекты |

## Ежедневный порядок работы

1. Создать или найти компанию, чтобы не создавать дубль.
2. Создать контактное лицо и связать его с компанией.
3. Создать сделку, указать услугу, сумму, ответственного и плановую дату закрытия.
4. После каждого контакта записать результат и создать следующее действие с датой.
5. Перемещать сделку по воронке только после выполнения критерия соответствующей стадии.
6. После победы создать связанный проект. После проигрыша указать причину.
7. В начале рабочего дня проверить свои просроченные задачи и сделки без следующего действия.

## Воронка продаж

| Стадия | Критерий входа | Следующее ожидаемое действие |
| --- | --- | --- |
| Новый запрос | Получено обращение или найден потенциальный клиент | Назначить ответственного и связаться |
| Квалификация | Контакт подтверждён | Проверить задачу, бюджет, сроки и соответствие профилю студии |
| Бриф / встреча | Клиент подходит студии | Собрать требования и участников решения |
| Оценка и предложение | Информации достаточно для оценки | Подготовить и отправить предложение |
| Согласование | Предложение отправлено | Согласовать объём, стоимость, сроки и договор |
| Выиграно | Клиент подтвердил начало работ | Создать проект и задачи запуска |
| Проиграно | Сделка закрыта без продажи | Указать причину и возможную дату возврата |

### Обязательные поля сделки

- название проекта;
- компания и основное контактное лицо;
- направление услуги;
- источник обращения;
- ответственный;
- ожидаемая сумма;
- плановые часы или себестоимость, если они уже известны;
- дата следующего контакта;
- предполагаемая дата закрытия;
- ссылка на бриф, папку или коммерческое предложение;
- причина проигрыша для закрытых неуспешных сделок.

### Направления услуг

На старте используется поле с выбором:

- разработка;
- дизайн;
- брендинг;
- маркетинг;
- сопровождение;
- аудит или консалтинг;
- другое.

Отдельный объект `Services` следует создавать только при появлении собственного прайс-листа, нормативных часов, ответственных и шаблонов работ для каждой услуги.

## Проекты

Для выигранных сделок создаётся объект `Projects` со связями с компанией, контактами и исходной сделкой.

### Поля проекта

- статус: `Подготовка`, `В работе`, `На проверке`, `Завершён`, `Приостановлен`;
- руководитель проекта;
- команда;
- дата старта и дедлайн;
- стоимость;
- плановые и фактические часы;
- ссылка на рабочий таск-трекер;
- ссылка на папку с файлами;
- дата следующего контрольного контакта с клиентом.

Не следует переносить в CRM каждую задачу разработки. В CRM фиксируются клиентские обязательства, контрольные точки и коммерческое состояние проекта.

## Рабочие представления

Необходимо создать следующие общие представления:

- `Новые необработанные запросы`;
- `Воронка команды`;
- `Сделки без следующего действия`;
- `Просроченные задачи`;
- `Предложения без ответа`;
- `Закрытие в этом месяце`;
- `Активные проекты`;
- `Проекты с риском просрочки`.

Для каждого менеджера создаётся личное представление `Моя воронка` с фильтром `Owner = Me`.

## Почта и календарь

Подключение выполняется через `Настройки → Аккаунты`. До массового подключения синхронизация проверяется на одном рабочем аккаунте.

Правила:

- синхронизировать только рабочие папки;
- не импортировать личную переписку;
- выбрать минимально необходимую видимость содержимого писем;
- сначала создавать контакты автоматически только по исходящим письмам;
- общий адрес подключать как отдельный почтовый ящик или через поддерживаемую пересылку;
- проверить, что письма и встречи правильно связываются с существующими людьми и компаниями.

## Роли и доступ

| Роль | Доступ |
| --- | --- |
| Администратор | Настройки, модель данных, интеграции и управление пользователями |
| Руководитель | Все клиенты, сделки, проекты и отчёты без системного администрирования |
| Сотрудник | Назначенные клиенты, сделки, задачи и проекты |
| Подрядчик | Только явно разрешённые проекты и необходимые поля |

В рабочем пространстве должен оставаться как минимум один администратор. Права на удаление, массовый импорт, экспорт и изменение модели данных выдаются только тем, кому они необходимы.

## Первые автоматизации

Автоматизации включаются по одной и сначала проверяются на тестовых записях:

1. Новый запрос создаёт задачу на первичный контакт.
2. Сделка без активности создаёт напоминание ответственному.
3. Отправка предложения создаёт задачу на последующий контакт.
4. Переход сделки в `Выиграно` создаёт проект и задачи запуска.
5. Просроченные задачи попадают в ежедневное уведомление.

Автоматическую отправку писем следует включать только после проверки получателей, шаблонов и условий запуска.

## Дашборд руководителя

Минимальный набор показателей:

- количество новых лидов;
- конверсия между стадиями;
- сумма открытой воронки;
- выигранная выручка за период;
- средний чек;
- распределение лидов по источникам;
- причины проигрышей;
- сделки без активности;
- активные и просроченные проекты.

## План внедрения

### Этап 1. Основа

- [ ] Назначить владельца CRM.
- [ ] Утвердить стадии и критерии переходов.
- [ ] Настроить компании, людей и сделки.
- [ ] Добавить обязательные поля.
- [ ] Создать личную и командную воронки.
- [ ] Настроить роли.
- [ ] Провести тестовую сделку от первого обращения до победы.

### Этап 2. Данные и коммуникации

- [ ] Очистить исходные таблицы от дублей.
- [ ] Импортировать сначала компании, затем контакты и связи.
- [ ] Подключить тестовые почту и календарь.
- [ ] Проверить видимость переписки и создание контактов.
- [ ] Пригласить пилотную группу из двух-трёх сотрудников.
- [ ] Провести обучение на реальных сделках.

### Этап 3. Проекты и автоматизации

- [ ] Создать объект `Projects` и его связи.
- [ ] Настроить создание проекта после выигранной сделки.
- [ ] Добавить напоминания о просроченных задачах.
- [ ] Добавить контроль сделок без активности.
- [ ] Проверить журнал каждого workflow перед массовым включением.

### Этап 4. Отчётность и запуск команды

- [ ] Создать рабочие представления.
- [ ] Настроить дашборд руководителя.
- [ ] Перенести все активные сделки.
- [ ] Зафиксировать еженедельный разбор воронки.
- [ ] Собрать обратную связь после двух недель использования.
- [ ] Удалить лишние поля и уточнить обязательные правила.

## Эксплуатационный чек-лист self-hosted

- [ ] Настроены постоянный домен и HTTPS.
- [ ] Настроен SMTP для служебных писем.
- [ ] PostgreSQL, Redis и файловое хранилище не доступны напрямую из интернета.
- [ ] Секреты не хранятся в репозитории.
- [ ] База данных и загруженные файлы копируются не реже одного раза в сутки.
- [ ] Резервные копии сохраняются вне основного сервера.
- [ ] Восстановление из резервной копии регулярно проверяется.
- [ ] Контролируются `/healthz`, свободное место и состояние server/worker.
- [ ] Используется зафиксированная версия контейнера, а не неконтролируемый `latest`.
- [ ] Перед обновлением создаётся резервная копия.
- [ ] Обновление сначала проверяется на тестовом экземпляре или копии данных.

Официальная Docker-конфигурация Twenty включает приложение, отдельный worker, PostgreSQL, Redis и постоянное файловое хранилище. Резервное копирование должно охватывать базу и файловое хранилище.

## Регламент качества данных

- У каждой активной сделки есть ответственный.
- У каждой активной сделки есть следующий шаг и дата.
- Результат встречи фиксируется в день встречи.
- Сделка перемещается только при выполнении критерия стадии.
- Выигранная сделка связывается с проектом.
- Для проигранной сделки обязательно указывается причина.
- Воронка разбирается командой раз в неделю.
- Дубли и устаревшие сделки проверяются не реже раза в месяц.
